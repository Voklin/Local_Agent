# 20. Локальная GGUF-модель внутри приложения

> Эта глава описывает исходный этап 6.0–6.0.1. Изменения 6.1: [JSON/KV и области чатов](25-json-tools-and-cache.md), [Мия/STT](26-miya-model-and-stt.md), [PC/Telegram](27-desktop-and-telegram.md).
В настройках модели появился отдельный раздел «GGUF внутри LocalAgent». Он запускает собственный установленный llama-server и связывает его с уже скачанным GGUF. Копирования моделей и автоматической установки runtime нет. Для внешнего LM Studio/Ollama остаётся обычный URL; кнопка остановки собственного сервера не управляет внешним приложением.

## Порядок работы

1. Выбрать доверенный llama-server через системный диалог. Это запускаемый бинарный файл; используйте официальную сборку llama.cpp с необходимыми DLL рядом.
2. Выбрать GGUF. Это ссылка на исходный файл; модель не переносится в каталог проекта.
3. Установить контекст (512–32768 токенов) и GPU-слои (-1–256). Безопасное начальное значение — 4096 и CPU (0); -1 просит сервер выгрузить все поддерживаемые слои на GPU.
4. Нажать «Запустить GGUF». Интерфейс показывает загрузку, PID, endpoint и ошибки. Загрузку можно отменить, работающий сервер — остановить.
5. После Ready нажать «Использовать в настройках»: endpoint/model попадают в черновик, временный API-ключ очищается. Проверить ответ и отдельно сохранить настройки. Сам запуск не меняет текущую конфигурацию агента.

При закрытии настроек сервер продолжает работать, при закрытии приложения завершается. Пути runtime/GGUF и автоматический запуск не сохраняются; после перезапуска требуется выбрать файлы заново. Сохранённый endpoint временного порта может стать недоступен: заново запустите сервер и примените новый адрес. Автоматического восстановления процесса/порта пока нет.

## Процессы и потоки

Main хранит только два пути, полученных из file picker. Renderer не может передать произвольный executable в start IPC. Core проверяет имя llama-server, существование файлов, расширение и первые четыре байта `GGUF`, integer/range параметров. Заголовок не доказывает совместимость модели: полный формат, архитектуру и chat template проверяет llama.cpp. Произвольные дополнительные аргументы из Electron не принимаются.

`RuntimeService.start` возвращает сразу, работа идёт в daemon thread. Состояния: stopped → starting → running; отмена/Stop → stopping → stopped; ошибка → error с ограниченным выводом. Второй запуск запрещён до завершения текущего worker. `runtime_status` не ждёт загрузки. Root проекта для модели не требуется; модельные файлы выбираются отдельно от файлового sandbox инструментов агента.

`LocalRuntime.start` привязывает процесс к `127.0.0.1` и временному свободному порту, передаёт --model, --ctx-size, --n-gpu-layers и --jinja. Readiness `/v1/models` проверяется с коротким HTTP timeout, общий cooperative deadline 120 секунд. Между операциями проверяется Event отмены. При ошибке/cancel/timeout завершается только созданный Popen, без поиска и убийства чужих процессов по имени/порту. Резервирование свободного порта и bind сервера разделены небольшим race window: конфликт приводит к ошибке запуска.

stdout/stderr объединены и постоянно читаются отдельным потоком порциями 1024 байта, включая вывод без newline. В памяти остаётся до 100 порций, UI показывает последние 4000 символов. Это устраняет заполнение PIPE при загрузке. Разделённая границей chunk UTF-8 буква может отображаться replacement-символом в диагностике; модельные ответы не проходят этот путь.

## Закрытие и аварии

На Windows `ProcessJob` создаёт ненаследуемый Job Object, задаёт JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE и присоединяет только собственный process handle. При гибели Core его job handle закрывается ОС и дочернее дерево завершается. Ошибка назначения job не игнорируется: запуск прекращается. На других ОС helper сейчас no-op; там гарантируется обычный Stop/graceful shutdown, но такой же crash-tree guarantee не заявляется.

Electron before-quit сначала проверяет dirty editor и Cancel. После разрешённого закрытия закрывает stdin Core и даёт до 15 секунд на cleanup; только после этого применяет fallback kill. Shutdown Core отменяет поиск, локальный runtime и задачу агента. После выхода Core повторный app.quit пропускается guard-флагом и завершает Electron. Это управление жизненным циклом, а не разрешение на запуск shell из модели.

Windows API: [Microsoft Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects). Аргументы сервера: [официальный llama.cpp server](https://github.com/ggml-org/llama.cpp/tree/master/tools/server).

## Доказательства и ограничения

Unit tests проверяют параметры, неблокирующий cancel, запрет второго старта, видимые ошибки, bounded logs, timeout cleanup и Windows job close/parent crash. Process bridge проверяет status/start validation/stop/health без модели. Отдельный Electron smoke при LCA_TEST_RUNTIME/LCA_TEST_GGUF выбирает реальные файлы, отменяет загрузку, повторно запускает, переносит endpoint, получает testModel и останавливает сервер, после чего продолжает остальные UI проверки.

Для реальной проверки 23 октября использованы официальный CPU runtime b11829 (zip SHA256 `C534F35CE9C842F3BC224FADAECC82E1B49768F63E8320922F6DBD603F66395E`, только тестовая папка) и уже существующий Qwen2.5-Coder-7B-Instruct-Q4_K_M. Модель ответила `42` за 2641 мс; GPU не использовался. LM Studio с qwen3.5-4b не останавливался. Runtime из backend LM Studio является его внутренним компонентом и не обязан запускаться как самостоятельный официальный llama-server.

Скачивание моделей, управление внешним LM Studio, выбор GPU по памяти, автоматический restart и packaged/clean-machine установка внешних DLL остаются отдельными работами. DLL/exe сервера не включаются в установщик LocalAgent.

### Windows venv и crash fixtures

У venv launcher Popen PID может отличаться от PID работающего интерпретатора (в проверке: 23180 и 14128). Старый process.kill в тесте иногда завершал только launcher; интерпретатор видел EOF и успевал корректно отменить approval, поэтому журнал показывал cancelled вместо ожидаемого interrupted. Crash fixture теперь создаёт собственный ProcessJob и при simulated crash закрывает всё своё дерево. Это не ослабление проверки восстановления: старые approval ID по-прежнему отвергаются и запись не повторяется.

Frozen Core также прошёл 11 process-сценариев с урезанным PATH и отдельный реальный GGUF lifecycle: Ready → ответ `42` за 4000 мс → Stop. Это проверка Core, а не чистой установки внешнего runtime на новой машине.

SHA256 скачанного CPU zip также совпал с digest соответствующего release asset официального GitHub API, а не только был вычислен локально.
