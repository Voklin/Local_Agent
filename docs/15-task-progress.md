# 15. План задачи, инструменты и результаты

## Пользовательский сценарий

После отправки задачи справа появляется панель «План задачи». Она показывает активный этап, последние вызовы инструментов и фактические результаты. При записи сначала виден статус «Ждёт решения», а успешная запись появляется только после результата `write_file` с `ok=true`. Отклонение, отмена, ошибка и неопределённая запись имеют разные состояния.

Панель можно свернуть, чтобы освободить место чату. Внутри длинного журнала есть отдельная прокрутка. Изменённые файлы собраны в раскрываемый список. При повторном выборе сохранённого чата панель получает тот же checkpoint; она не собирает состояние из текстового лога. Для paused сохраняется существующая кнопка продолжения.

## Границы этого обновления

Это наблюдаемость существующего исполнения, а не новый интеллектуальный планировщик. `build_plan` по-прежнему создаёт исходный список этапов эвристикой по prompt. Приложение не получает shell tool, запуск тестов, MCP transport или новые разрешения на запись. Проверка завершённости моделью не является запуском тестов; интерфейс прямо напоминает об этом.

Статус этапа «Завершён» означает, что ядро перешло дальше. Он не означает успешность каждого инструмента внутри этапа: для этого нужно смотреть его результат. Общий completed означает завершение ответа агента, а не независимую приёмку пользовательского проекта.

## Этапы исполнения

Начальный analysis становится active при входе в цикл. Перед `list_files`, `read_file`, `search_text` и неизвестным tool ядро переходит в research; неизвестный tool затем получает обычный отказ исполнителя. Перед `write_file` активируется implementation. Если эвристический план не содержал этот этап, он добавляется перед verification. Отсутствие слова действия в запросе больше не скрывает реальное предложение записи.

`set_stage` закрывает прежний active как done, помечает непосещённые предыдущие pending как skipped и активирует выбранный этап. Возврат из реализации к чтению поддерживается: research снова active, а предыдущая реализация остаётся завершённой. Одновременно активен один этап. При завершении pending становятся skipped; приложение больше не объявляет все отсутствовавшие действия выполненными.

Verification соответствует существующему пути ответа/модельной проверки завершённости, finish — формированию итогового состояния. Числа max_turns отдельных этапов всё ещё не управляют отдельными интеллектуальными подзадачами. Исторические checkpoint с прежними done не пересчитываются задним числом: их точность ограничена старой версией кода.

## Структура журнала

Новые задачи добавляют `tool_activity`, `activity_sequence` и `activity_omitted`. Это опциональное расширение JSON версии 2; старые записи без этих полей продолжают открываться.

| Поле операции | Значение |
| --- | --- |
| `id` | Внутренний возрастающий номер в пределах задачи, сохраняемый между resume |
| `tool`, `path` | Имя инструмента и краткий путь; содержание файла, query и полный JSON аргументов не копируются |
| `call_id`, `message_index` | Корреляция с конкретным assistant-блоком в канонической истории |
| `stage` | Этап, на котором началась операция |
| `status`, `summary` | Структурное состояние и ограниченная по длине сводка для UI |
| `started_at`, `finished_at` | UTC-время начала и терминального результата |

Журнал хранит последние 100 операций. При удалении старых метаданных увеличивается activity_omitted; UI сообщает, что более ранние операции следует искать в полной истории. Канонический transcript при этом не обрезается. Путь ограничен 500 символами, имя tool — 80, summary — 500. Это ограничение метаданных панели, а не новый лимит содержимого файла или HTTP-ответа.

## Состояния и порядок сохранения

| Состояние | Что подтверждено |
| --- | --- |
| `running` | Вызов принят ядром, результат ещё не сохранён |
| `awaiting_approval` | Diff подготовлен; требуется решение пользователя |
| `applying` | Получено согласие и начата запись; её успех ещё не подтверждён |
| `succeeded` | В соответствующем tool result есть ok=true |
| `rejected` / `cancelled` | Получен USER_DENIED / USER_CANCELLED |
| `failed` | Исполнитель вернул ошибку, включая FILE_CHANGED |
| `interrupted` | После прерывания нет сохранённого результата; согласие не переносится |
| `unknown` | Запись могла произойти до сбоя; требуется проверить файл |

Перед вызовом ядро создаёт metadata-запись и сохраняет checkpoint. Для записи перед показом approval сохраняется awaiting_approval, перед непосредственной записью — applying. После исполнения сначала публикуется канонический tool result в сообщениях, затем `finish_tool` формирует сводку и следующий checkpoint фиксирует итог. Поэтому crash между этими сохранениями можно согласовать по архиву, не принимая старое совпадение call_id за новый успех.

Сводка чтения содержит число символов; обзор и поиск — число элементов/совпадений, с отметкой о лимите выдачи. Успех записи обозначается «Файл записан». Содержимое файла или найденные строки в metadata не копируются, но они по-прежнему могут находиться в каноническом чате. Ошибки и пути тоже могут раскрывать сведения о проекте — это служебные данные, а не обезличенный отчёт.

## Восстановление

`recover_tools` рассматривает только активные операции. Он проверяет assistant-сообщение по сохранённому индексу, наличие нужного call_id в этом блоке и последующие непрерывные tool results. Результат из другой части истории с повторённым ID не используется. Если найден валидный JSON result, восстанавливаются его статус и сводка; иначе applying становится unknown, а running/awaiting_approval — interrupted.

Восстановление идемпотентно: повторное открытие не меняет уже терминальную операцию. Механизм pending_write, snapshot и новых approval IDs сохраняется; журнал не является полномочием на повторную запись. Сервис также согласует незавершённые записи при неожиданном выходе worker, чтобы UI не оставался со статусом «Выполняется» после task_end.

## Проверки

Unit-тесты проверяют лимит, отсутствие raw content, последовательные ID, разные исходы, пропущенные этапы, повторённые call_id и идемпотентность восстановления. HTTP-интеграция проверяет сохранённый awaiting_approval до Apply и итоговые succeeded/rejected/failed вместе с историей. Настоящий subprocess kill при approval подтверждает interrupted после открытия новым процессом.

Скрытый Electron smoke проверяет активную реализацию до Apply, успешную запись в панели, skipped research, повторное открытие журнала и ошибку конфликта. Снимок completed.png позволяет отдельно проверить компоновку. CI выполняет Python-регрессии и пересобирает frozen Core; обновлённый модуль попадает в Windows-пакет обычным импортом.

Реальная модель в этой итерации не проверена: при обращении к LM Studio localhost:1234 сервер отклонил соединение. Этот отказ отражён в WORK_PLAN и не заменён утверждением об успешной модели. Сценарии tools/approval/recovery проверяются действующими HTTP-фикстурами.

Отдельная HTTP-регрессия проверяет несколько tools в одном assistant-ответе: read_file, затем write_file. Индекс исходного assistant-блока фиксируется один раз до цикла, а не пересчитывается после каждого добавленного tool result. Тот же anchor используется pending_write и журналом; при разрыве между результатами и checkpoint успешная запись восстанавливается без ложного unknown.
