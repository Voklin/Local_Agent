# 12. Как развивать проект и документацию

## Перед изменением

Определите пользовательский сценарий, слой ответственности и наблюдаемый критерий готовности. Пример: «при сохранении модели после перезапуска восстанавливается ID, а ключа нет в JSON». Такой критерий проверяется точнее, чем «настройки улучшены».

Проверьте `git status`, прочитайте нужную главу и конкретный исходник. Не начинайте с редактирования большого файла-эталона дизайна, если изменение относится к действующему приложению. Не смешивайте исправление поведения с массовым форматированием несвязанных модулей.

## Где менять конкретную функцию

| Требование | Основные файлы | Проверка |
| --- | --- | --- |
| Новый UI-элемент | `App.tsx`, `style.css` | TypeScript, сборка, визуальная и сценарная проверка |
| Новая команда UI → Core | Preload, main, `vite-env.d.ts`, `bridge.py`, сервис | Сквозной round-trip и отказ неверных параметров |
| Новое событие Core → UI | `TaskService`, callback движка, React subscription | ID, порядок, завершение/отмена |
| Новый файловый инструмент | `tools.py`, `TOOL_DEFINITIONS`, `AgentEngine` при approval | Разрешённые/запрещённые пути и отсутствие side effect до разрешения |
| Поведение генерации | `engine.py`, `model_client.py` | HTTP-фикстура, streaming, tools, отмена и закрытие |
| Новое сохраняемое поле | Соответствующий store и валидация | Старый/повреждённый JSON, round-trip, отсутствие секретов |
| Новая стадия задачи | `planner.py`, `task_store.py`, реальные вызовы engine | Не только наличие stage, но и наблюдаемый переход |
| Поддержка провайдера | Config/SDK protocol/сервер | Проверка фактической совместимости, не только названия |

## Пример: новая команда чтения

Предположим, нужно вернуть метаданные открытого файла. Сначала определите вход (`path`) и выход (`size_bytes`, дата, тип). Решите, нужна ли эта команда модели или только UI. Для UI добавьте фиксированную preload-функцию, main handler, тип и Python dispatch. В Python используйте проверенный путь внутри проекта, не произвольный путь из renderer.

Добавьте пример в [контракты](08-protocols.md), описание функции в annotations и тест доступа за пределами корня. Не публикуйте общий `callPython(method, params)` ради одной операции: он расширит полномочия всех будущих renderer-вызовов.

## Пример: новый изменяющий инструмент

Для rename, delete или создания каталогов недостаточно скопировать `write_file`. Нужно определить preview, решение пользователя, конфликтующие изменения, ошибки и поведение отмены. Инструменту нужны описание для модели и реализация; чувствительная операция должна получать разрешение от проверяемого UI-пути, а не из пользовательского JSON `approved: true`.

Проверяйте три состояния: до согласия, после отказа, после применения. Отдельно тестируйте устаревший ID и подмену пути. Для операции с несколькими файлами определите частичный успех и восстановление заранее.

## Git и pull request

Рабочая ветка текущей разработки — `codex/electron-agent-bridge`; изменения предложены в [PR #1](https://github.com/Voklin/Local_Agent/pull/1). Этот текст не утверждает, что PR уже объединён с `main`.

Обычный рабочий процесс: изменить код → выполнить относящиеся к изменению проверки → изучить diff → создать коммит → отправить ветку → проверить CI. Коммит фиксирует содержимое; он сам не запускает вашу локальную модель. Успешная публикация ветки не означает успешный CI до его завершения.

PR-описание должно объяснять конечное поведение для читателя, не видевшего чат. Если возможности меняются, перепишите описание целиком и укажите реальные проверки и оставшиеся ограничения. Не переносите секреты из логов и пользовательские исходники из тестового проекта в публичное описание.

## Документация как часть изменения

Документация состоит из трёх слоёв:

1. **Ручные объяснения**: главы, сценарии и ограничения. Они отвечают на вопросы «почему», «когда» и «какая гарантия».
2. **Ручные аннотации**: `tools/doc_notes.py` описывает назначение файлов и объявлений.
3. **Генерируемая структура**: `tools/generate_code_reference.py` читает Python AST и TypeScript AST, извлекает реальные имена, сигнатуры и строки и создаёт справочники.

После изменения объявления обновите аннотацию, затем выполните:

```powershell
python tools/generate_code_reference.py
python tools/check_docs.py
```

Если изменилось только объяснение, достаточно проверки ссылок и структуры. Не требуется запускать модель или заново выполнять сетевые тесты приложения ради исправления абзаца.

## Что контролирует проверка документации

Проверка ищет сломанные локальные Markdown-ссылки и source line links, незадокументированные исходные файлы/объявления и устаревший генерируемый справочник. Она не доказывает семантическую истинность абзацев. Рецензент всё равно должен сопоставить описание с реализацией.

Для источников данных используйте код, lock-файл и Git. Не присваивайте новому этапу выдуманную дату и не называйте библиотеку используемой в рабочем пути только потому, что она встречается в старом списке зависимостей.

## Когда обновлять какие главы

Изменение API требует главы 8; состояния на диске — главы 9; нового потока/процесса — главы 3; нового алгоритма — главы 6. Устранение ограничения должно убрать или скорректировать соответствующий пункт главы 11. Значимое функциональное завершение добавляется в историю с проверенным commit SHA и результатами проверок.

Сохраняйте примеры небольшими и явно учебными. Настоящие UUID, ключи и абсолютные пути пользователя не нужны для объяснения контракта. Команды установки должны работать из указанного каталога, а материал о технологиях должен показывать, где именно они встречаются в проекте.
