# Аудит LESHY / LocalAgent — 3 ноября 2026

## Вывод

Проект имеет развитое ядро локального coding agent и несколько работающих интерфейсов. Основной риск следующего этапа — расхождение между текущими исходниками, автоматическими проверками, документацией и поставляемой сборкой. Рекомендуемый приоритет: восстановить достоверный baseline и приёмку поставки, затем улучшать восстановление задач и измерять качество модели. Переписывание ядра или добавление ещё одного планировщика не обосновано.

Аудит относится к текущему дереву `LocalAgent`, HEAD `9572082`, а не к соседней архивной копии и не к опубликованному installer. На входе: 97 изменённых tracked-файлов и 213 untracked-записей Git (каталоги могут объединять несколько файлов). Это риск воспроизводимости, само по себе не дефект исполнения. Исходники приложения при аудите не исправлялись.

## Метод и достоверность

Прочитаны конфигурации сборки/CI, основные точки Electron/Core, исполнение инструментов, бюджет, реестр запусков, хранение, новая IDE-панель, существующие тесты и отчёты. Запущены production build, Python unit/migration suites, docs check и изолированное воспроизведение ошибки launcher.

- **Подтверждено запуском** — получен текущий результат команды или минимального воспроизведения.
- **Подтверждено исходниками** — обнаружено прямое расхождение контрактов или конфигураций; последствия в полном installer могут требовать отдельного запуска.
- **Риск сопровождения** — инженерная оценка, не доказанная пользовательская поломка.
- **UNVERIFIED** — текущей проверки нет. Старые отчёты не превращаются в свежие результаты.

Логи этого аудита: `artifacts/audit-2026-11-03/`. Первые Python-запуски внутри песочницы остановлены: диагностический стек показал зависание в `socket._fallback_socketpair → asyncio.new_event_loop`, до inference. Для вывода о проекте используются повторные запуски вне песочницы; ошибки первого запуска не считаются подтверждёнными регрессиями продукта.

## Подтверждённые проблемы

### A1 — P1: обязательная проверка документации падает

**Доказательство запуска:** `.venv/Scripts/python.exe tools/check_docs.py` завершилась с кодом 1: `ValueError: Нет назначения файла: apps/desktop/ide.html`.

**Причина:** `tools/generate_code_reference.py` включает tracked и untracked-файлы, а `file_description()` требует аннотацию нового файла; покрытие `tools/doc_notes.py` отстаёт от текущих entrypoints. `check_docs.py` вызывает `render()` до проверки ссылок, поэтому до остальных ошибок документации этот запуск не дошёл. Та же команда обязательна в CI.

**Действие:** добавить точные аннотации новых исходников, пересоздать справочники, затем исправить все обнаруженные ссылки. Критерий: полный `docs:check` завершается с кодом 0, без исключения новых файлов из каталога ради зелёного результата.

### A2 — P1: package smoke использует прежнее имя executable

**Доказательство исходниками:** `electron-builder.json:3` задаёт `productName: LESHY`; `tests/electron/packaged-smoke.mjs:168` по умолчанию ищет `artifacts/windows/win-unpacked/Neutral.exe`. Workflow вызывает его без аргумента на строке 63.

**Последствие:** при чистой сборке с новым именем проверка обращается к отсутствующему старому executable; при оставшемся старом файле возможна проверка старой сборки. Полный новый installer в этом аудите не собирался, поэтому фактическое падение свежего packaging job — **UNVERIFIED**, конфигурационное расхождение подтверждено.

**Действие:** получать путь из конфигурации/манифеста сборки либо передавать его явно; проверять идентичность и версию созданного артефакта. Приёмка — на чистом output-каталоге.

### A3 — P1: launcher может сообщить успех после аварийного завершения теста

**Доказательство запуска:** обработчик из `tests/electron/run.cjs` выполнен в Node VM с подменённым `spawn`. Вызов `exit(null, 'SIGTERM')` дал `process.exitCode === 0`.

**Причина:** `child.on('exit', code => { process.exitCode = code || 0; })` теряет сигнал и трактует `null` как успех.

**Действие:** успех только при `code === 0` и отсутствии сигнала; обработать spawn error и завершение по сигналу ненулевым кодом. Добавить отдельные сценарии 0, nonzero, signal и spawn error. Воспроизведение не доказывает, что прежние GUI-прогоны аварийно завершались; оно доказывает ненадёжность текущего сигнала успеха.

### A4 — P1: CI не защищает основной новый путь IDE

**Доказательство исходниками:** `.github/workflows/validate.yml` запускает `neutral-smoke.cjs` и `studio-layout.cjs`, но не `neutral-ide-integration.cjs`, `background-runs-smoke.cjs` и `leshy-themes.cjs`. Последние доступны в репозитории. `run.cjs` добавляет `--legacy-ide` всем сценариям, имя которых не содержит `neutral-ide`.

**Последствие:** зелёный desktop smoke не подтверждает запуск новой Code-OSS IDE, webview → Core → editor, Ask/Plan, применение diff и Ctrl+Z. Это пробел покрытия CI, а не доказательство поломки новой IDE.

**Действие:** добавить обязательный native IDE gate после подготовки runtime и короткие проверки background isolation и тем. Полную визуальную матрицу можно вынести в отдельный job. Сначала исправить A3.

### A5 — P2: опубликованные внутри проекта статусы противоречат текущей реализации

**Доказательство:** `docs/57-roadmap-v2.md:4` оставляет Core→editor gate открытым; `docs/75-ide-panel-rebuild.md` описывает его прохождение 2 ноября. `docs/11-current-status.md` утверждает отсутствие command tool и описывает прежнее JSON-хранение, хотя сейчас существуют `run_project_command`, SQLite и новые evidence-контракты. README начинает описание с Neutral, packaging — LESHY.

**Последствие:** пользователь и следующий разработчик получают разные представления о доступных функциях и готовности. Обновление дат само по себе проблему не решит.

**Действие:** один актуальный статус с ссылками на доказательства; старые главы явно обозначить историческими там, где их контракты заменены. Не менять технические идентификаторы приложения и пути профиля без отдельной миграции.

### A6 — P2: новая IDE имеет явные пробелы функционального паритета

**Доказательство исходниками и собственной документацией:** `docs/75-ide-panel-rebuild.md:26` фиксирует отсутствие расширенных редакторов плана, правил и MCP в новой панели. Повреждённый журнал и неизвестный исход отката блокируют работу; универсального восстановления нет.

**Последствие:** длинная задача может потребовать перехода в главное окно или ручной диагностики. Само блокирование неопределённого действия оправдано; улучшать следует доступность диагностики и понятный путь восстановления.

**Действие:** составить таблицу пользовательских сценариев и места их настройки; обеспечить переход из IDE к нужной настройке. Для повреждений сначала экспорт диагностики и объяснение, затем отдельно проектировать безопасное восстановление. Запрещено автоматически повторять действие с неизвестным эффектом.

## Риски сопровождения и открытые измерения

- `agent/engine.py` — 996 строк и много взаимосвязанных обязанностей; `core/python/bridge.py` — 393 строки маршрутизации. Разделять постепенно по фактическим изменениям, с сохранением контрактов, без массовой переписи.
- `idePanel/workspace.tsx` — 92 очень плотные строки с состоянием, событиями, подключением, историей и UI; важные данные `task`, `approval`, `config`, history используют `any`. Typecheck не доказывает их соответствие runtime payload. Это риск, не воспроизведённая ошибка.
- Профили модели и качество native/JSON нужно оценивать на одинаковых fixtures с oracle. Исторические успешные примеры и описанный неуспешный multi-file benchmark не дают статистики надёжности текущей версии.
- Полный installer текущего LESHY, новая установка/обновление, длительные реальные задачи, внешние API, контейнеры и пиковые VRAM/RAM — **UNVERIFIED** в этом аудите.
- Текущая визуальная и accessibility-приёмка — **UNVERIFIED**: свежие окна здесь не открывались. Старые LESHY-скриншоты не являются текущей проверкой.
- Аудит зависимостей на CVE и лицензий сторонних компонентов не проводился; выводов об их безопасности и актуальности нет.

## Направление развития

Предлагаются три возможных приоритета: поставка и воспроизводимость; качество автономных задач; расширение IDE/голоса/провайдеров. Рекомендована последовательность **поставка → качество → расширение**: первые два этапа дают основу, по которой можно измерять полезность новых функций. Это предложение аудита, не ранее согласованное продуктовое решение.

Подробная очередь с файлами, проверками и критериями — [план развития](superpowers/plans/2026-11-03-project-development.md). Статусы старого roadmap не следует механически переносить в новый план.
