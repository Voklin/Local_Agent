# 64. Независимые фоновые чаты — следующий срез 11b

> Историческое состояние промежуточной поставки. Полный этап 11 завершён: [актуальные контракты и проверки](66-stage11-complete.md).

Дата: 28 октября 2026. Продолжение [11a](63-run-registry-scheduler-ledger.md)
по [Roadmap V2](57-roadmap-v2.md). Реализованы отдельные владельцы исполнения и
переключение чатов. Полный этап 11, subagent executor и resource placement ещё не закрыты.

## Как пользоваться

Во время ответа можно открыть другой разговор или создать новый, переключиться
между Chat, IDE и Лолой. Слева появляется раздел **«В работе»**: он показывает
активные задачи и помечает запросы, ожидающие решения. Нажатие открывает нужный
режим и чат с актуальным ответом и кнопкой остановки.

Другой чат может поставить запрос в общую очередь. Одновременно выполняется одна
генерация; ожидание подтверждения не удерживает inference lease. **«Остановить»**
относится только к открытому запуску. Отмена запроса в очереди снимает reservation
без HTTP и не отменяет соседа. Новых лимитов токенов или времени local auto нет.

В окне подтверждения добавлена кнопка **«Решить позже»**. Она скрывает окно,
оставляя действие неразрешённым. Можно заняться другим чатом. Возврат через
«В работе» снова показывает тот же preview и тот же approval ID. Передача файлов
внешней модели по-прежнему требует явного решения по полному предпросмотру.

Изменение подключения, прав, расширений и проекта, удаление/перенос/переименование
чатов остаются заблокированы, пока работает хотя бы один запуск. Повторное сохранение
**идентичных** настроек модели допускается без записи — composer использует этот
путь перед запросом. Изменённые настройки требуют завершить активную работу.
Фоновые запуски в этом MVP используют одинаковые URL, model ID и API protocol.
Разные модели автоматически не загружаются и не выгружаются.

В одной папке проекта разрешён один IDE owner. Пересекающиеся родительские/дочерние
корни также конфликтуют; пути сравниваются после resolve. Это предотвращает
конкурирующие правки через два чата, не подменяя guards fingerprint/approval.
Несвязанные корни поддержаны на уровне TaskService; переключение workspace в UI
во время работы пока закрыто. Выбор другого режима или чата текущего workspace разрешён.

## Архитектура и файлы

| Компонент | Ответственность |
| --- | --- |
| `core/python/task_service.py` | Координатор UI selection, общий lock, каталог owners, проверки допуска, проекции выбранного engine/approval, shutdown всех запусков. |
| `core/python/run_session.py` | Собственный canonical chat, SessionService, frozen config, operation, engine/thread, run context, stream timers и pending approval одного запуска. |
| `core/python/task_execution.py` | Перенесённый существующий engine loop: dispatch tools, callbacks, persistence, external/write approvals и финализация. |
| `core/python/session_service.py` | Загрузка сохранённых чатов и crash recovery. Для живого owner coordinator возвращает live view и не запускает recovery. |
| `agent/inference_scheduler.py` | Прежний единый process-wide арбитр HTTP inference; отдельной конкурирующей GPU очереди не создано. |
| `apps/desktop/src/App.tsx` | Каталог фоновых задач, выбор live чата, восстановление UI, буфер событий при смене и решение позже. |
| `apps/desktop/src/ConversationSidebar.tsx` | Разделяет блокировку изменений каталога и разрешённую навигацию. |
| `core/python/bridge.py`, Electron main/preload | Фиксированный RPC `active_runs`, scoped cancel с run ID, передача live snapshot. |

Координатор **не наследует execution loop**. Каждый RunSession получает свои
callbacks и состояние; его `chat` не следует за выбором пользователя. Общие
ExtensionService, AssistantService, desktop adapter, ProjectStore и registry
переиспользуются. Их глобальная конфигурация блокируется на время исполнения.

Свойства `engine`, `thread`, `run_id`, `approval` координатора сохранены как
совместимые проекции выбранного owner для существующих контроллеров и проверок.
`task_running` означает наличие **любого** живого запуска. Завершённые невыбранные
owners освобождаются при последующей навигации/запуске после выхода их потока;
SQLite история запусков при этом не удаляется.

`RunSession.begin` создаёт отдельный OperationContext через локальный admission gate,
который не является GPU lease. Ошибка старта закрывает run telemetry и таймеры.
`TaskService.shutdown` сначала запрещает новые задачи и отменяет всех owners,
включая невидимые и ожидающие очередь, затем ждёт cleanup и закрывает общие службы.
Неизвестные side effects по-прежнему требуют journal recovery; автоматического replay нет.

## Возврат к потоку без потерь

Каждый execution event получает возрастающий `event_seq` под control RLock,
а также chat/run/mode/root. Live snapshot содержит последний cursor,
canonical history, текущий незавершённый текст с прежним `message_id`, checkpoint
и полное ожидающее подтверждение. Незавершённый текст в `view()` не записывается
дополнительным сообщением в SQLite.

При загрузке renderer временно буферизует события целевого чата. После snapshot
он восстанавливает message IDs и применяет только события новее snapshot cursor.
Так delta между чтением snapshot и доставкой IPC response не теряется и не дублируется.
Завершённые run IDs исключаются из поздних каталогов, чтобы старый snapshot не
возвращал завершённую задачу в список «В работе».

Обычные события другого чата не меняют открытые сообщения, approval и busy.
Подтверждённая правка фонового IDE запуска обновляет уже открытый редактор той же
папки через существующий refresh/conflict механизм, даже если открыт другой чат.
Устаревший Stop с чужим run ID отклоняется. Таймаут RPC старта передаёт исходный
run ID в cancel, вместо остановки случайно выбранного к тому времени чата.

## Подтверждения, Лола и Telegram

На каждый owner приходится своё pending событие и approval ID. Решение принимается
только для выбранного owner и точного сочетания run/approval ID; переключение не
является разрешением записи, MCP, программы или передачи исходников.

Лола сохраняет прежнюю передачу только coding задачи. Пока целевой запуск возвращает
результат в исходный voice чат, новый запуск исходного чата блокируется: это исключает
потерю записи результата из-за одновременного сохранения двух histories.

Telegram больше не подхватывает approval постороннего фонового чата. Удалённый
контроллер сохраняет прежнюю модель работы с выбранным разговором; отдельный
селектор фоновых runs и независимая навигация Telegram в этот срез не входят.
Если UI перешёл в другой чат, команды Stop/approval требуют вернуться к разговору
Telegram и не затрагивают соседнюю задачу.

## Проверки и воспроизведение

`tests/migration/test_background_runs.py` запускает настоящие AgentEngine workers
и локальный HTTP сервер в изолированном профиле. Проверены:

- два активных чата при одном физическом HTTP, live snapshot без crash recovery;
- Stop очереди без HTTP, продолжение первого потока и отсутствие чужих сообщений;
- разные approvals в двух корнях, отказ чужого решения и сохранение только разрешённого файла;
- запрет второго writer в том же и вложенном корне;
- отказ разных model bindings и shutdown обоих owners с освобождением scheduler.

`tests/electron/background-runs-smoke.cjs` проходит renderer → preload → main →
Python/Core → HTTP. Он специально задерживает IPC load **после** чтения snapshot
и добавляет реальную SSE delta. Ответ остаётся одним сообщением с обеими частями.
Затем Stop второго чата не отправляет его HTTP, а первый завершается. Кадр:
`.test-data/background-gui/two-chats.png`; результат и request count рядом.

Существующий `neutral-smoke.cjs` дополнен «Решить позже» → возврат к тому же
подтверждению без нового HTTP. Его искусственное source-preview событие явно
не задаёт cursor: повтор реального старого cursor теперь правильно игнорируется.
Fault injection сохранения перенесён с task_service в task_execution вместе с кодом;
отказ хранения по-прежнему не разрешает запись файла.

При полном Core/HTTP прогоне найдена и исправлена регрессия отмены discovery:
координатор Stop снова отменяет загрузку списка моделей, даже без выбранного owner.
HTTP fixture дополнен обычным non-stream ответом для auxiliary memory request;
нештатные server tracebacks не используются как доказательство успешного HTTP.

## Миграция, ограничения и следующий шаг

Новой миграции нет: используется schema v3 из 11a. Канонические сообщения,
TaskStore, RunState, CallJournal, StageVerifier, WorkspaceAccessPolicy, source
approval и RequestBudget сохраняют свои роли. Старые checkpoints не объявляются
живыми только на основании статуса: живым owner считается объект текущего процесса.
После перезапуска Core работает существующее консервативное recovery без повторения effects.

Это **фоновые чаты**, а не готовый executor субагентов. В оставшейся части 11 нужны
настоящий parent/child handoff и join, recovery исполнения дерева, resource groups и политика
размещения/OOM для разных моделей. Следующий срез [11c](65-process-identity-and-restart.md) добавил process identity
и проверку kill/restart нескольких чатов; executor дерева этим не реализован.
Денежная политика платных API отдельно от ledger
не реализована. Межпроцессного scheduler и управления внешним LM Studio/VRAM нет.

Перезагрузка/падение renderer сохраняет прежнее поведение Electron: selected task
получает Stop; гарантия переключения относится к обычной навигации живого UI.
Закрытие Core не оставляет фоновые задачи автоматически исполняться после restart.
Для модели без native tools quality gate главы 59 остаётся открыт.

В этом срезе не запускался дополнительный live LLM benchmark: контракт очереди,
изолированных histories и IPC проверен детерминированно, это не оценка качества модели.
Установщик, commit/push, merge/release и установка поверх приложения не выполнялись.
Существующие изменения и пользовательский `docs.zip` сохранены.
