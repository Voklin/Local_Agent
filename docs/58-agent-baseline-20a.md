# Этап 20a: воспроизводимый baseline реального агента

27 октября 2026. Первая поставка по [Roadmap V2](57-roadmap-v2.md).
Изменения приложения пока не активируют индекс, Context Builder или субагентов.
Сначала измеряется существующий Agent; его Agent/Core исходники заморожены в
каждом каталоге результата. Установщик не собирается.

## Контракты окончательного review

Рабочая копия V2 перенесена в главу 57. В ней зафиксированы решения:

- MVP 13a/14a работает с сохранёнными файлами. Unsaved overlays требуют отдельного
  DocumentService и версий в ContextPack → preview → apply; текущий dirty guard
  не обходится.
- Evidence исполнения, scope/witness и полнота/актуальность покрытия разделяются.
  Неполная workspace revision не становится full success. Конкретная реализация
  versioned receipts и миграции ещё впереди; нынешний verifier не ослаблен.
- В MVP 11/12 ребёнок наследует модель/подключение родителя. Разные модели требуют
  отдельной residency/OOM-политики. Сам inference lease не освобождает VRAM.

Это принятые проектные решения, а не уже реализованные новые сервисы.

## Инструмент baseline

[benchmark_agent.py](../tools/benchmark_agent.py) создаёт только собственные
synthetic projects. Существующий каталог результата не перезаписывается. Перед
созданием fixture сохраняются Agent/Core Python исходники, requirements, сам
runner, commit HEAD и SHA-256 каждого файла в `baseline-sources.zip` и `report.json`.
Dirty working tree фиксируется явно: один Git commit не описывает весь baseline.

Проекты содержат 40 / 1200 / 12000 несвязанных Python/JS/TS filler-файлов и
небольшой пакет `app`. Он включает функцию расчёта и вызывающий модуль. Есть
синтетический защищённый путь с `.neutralignore`; настоящие секреты и пользовательские
проекты не используются. Путь source известен независимому oracle, но не сообщается
модели в задании.

Для каждого размера проверяются:

1. Definition: точное `path:line`, полученное после успешного file/search tool,
   без записи. Угаданный путь или текст «сейчас вызову tool» не считаются успехом.
2. References: реальное место вызова вне определения, с provenance.
3. Bugfix: минимальная правка коэффициента налога 10% → 20%, сохранение контракта.
4. Multifile: переименование определения и согласованная правка импортирующего
   вызывающего модуля.
5. Recovery: Stop перед первым approval, проверка отсутствия изменений и повторный
   Engine с тем же checkpoint/journal. Это **не** kill процесса и не проверка
   неизвестного эффекта после аварии; такие дополнительные LLM-сценарии остаются
   вне покрытия этого первого baseline.

Модель получает существующие file/search/read/range/write/patch tools, обычные
Engine/ToolExecutor/CallJournal/approval. Shell и внешний MCP не предоставляются.
Автоподтверждение действует только для двух исходников созданного fixture. Профиль
TaskStore/журналов изолирован в каталоге результата. Main app settings не меняются.

Проверка кода независима от ответа модели: AST проверяет узкий заранее заданный
контракт функции и caller; вычисляется только разрешённое арифметическое выражение
с пустым `__builtins__`. Сгенерированный модуль не импортируется и его произвольные
эффекты не исполняются. Контракт намеренно ограничен минимальным решением задачи,
а не используется как универсальный проверяющий произвольный Python-код.

## Метрики и чтение отчёта

`report.json` сохраняется атомарно после каждого сценария. После прогона появляется
таблица `report.md`. Поле `completed` — результат цикла Agent, не независимый PASS.
PASS требует корректной задачи, diff, отсутствия ошибок и завершённого цикла.
Сохраняются полные transcripts/receipts для разбора ложного завершения.

Считаются настоящие inference POST attempts через HTTP hook, включая транспортные
повторы и служебные completion checks. Отдельно записываются reported input/output
tokens, количество reported responses, tool calls, approvals, wall time и изменённые
файлы. VRAM samples относятся ко всему устройству, не выдаются за точный model peak.
CPU/RAM process profiling пока не добавлено.

Лексический поиск до index имеет 9 повторов с тёплым filesystem cache: p50, p95,
Recall@10, scanned files, truncated/reason. Высокий Recall@10 на этих простых fixture
не означает полный обход большого проекта. Проверки LLM имеют по одному trial:
по ним нельзя объявлять статистическую неухудшаемость или универсальную поддержку
произвольных реальных репозиториев.

## Модели и загрузка

Пользователь выбрал Ornith 1.5 9B Q5_K_M для baseline и Qwen2.5-Coder 7B Instruct
для JSON без native tool calling. Одновременно загружается только одна модель;
выгрузка подтверждается `list_loaded` перед загрузкой следующей. Пользователь
разрешил настраивать load configuration по необходимости.

Аппаратный профиль: NVIDIA RTX 5070, 12 227 MiB VRAM, около 32 GiB системной RAM.
Начальный Ornith pilot использовал GPU ratio 0.8. Перед основным прогоном профиль
зафиксирован: context 8192, GPU ratio 1.0, strict VRAM cap, KV на CPU, eval batch
128, Flash Attention, seed 0; temperature 0, top_p 1. Фактический SDK load config
дополнительно показал Q8_0 для K/V. Native API показывает inherited parallel=4,
но runner отправляет только один inference одновременно. Другие load параметры
не объявляются изменёнными, если API этого не подтвердил.

Runner использует фиксированные конечные пределы эксперимента: до 10 turns,
3 минуты на один Engine и до 1536 output tokens. Это условия измерения; они не
переносятся в пользовательский auto-режим и не являются новой системой его лимитов.

Qwen первоначально не загружалась из-за отсутствия второго GGUF shard. Первая часть
проверена по SHA-256, недостающая часть 1 454 989 568 байт восстановлена из
[официального репозитория Qwen](https://huggingface.co/Qwen/Qwen2.5-Coder-7B-Instruct-GGUF/tree/13fb94bfda8c8cf22497dc57b78f391a9acb426a).
Окончательное имя присвоено только после проверки размера и SHA-256.
Существующая первая часть не заменялась. Загрузка и hashes записаны в
`.test-data/qwen25-shard-repair.log`; файлы весов не добавляются в Git.

## Результаты

Все три исходных прогона завершены до изменений JSON-ядра:

| Модель / протокол | Верная задача и diff | Полный E2E PASS | Cutoff эксперимента | Inference POST | Вход / выход, tokens | Секунды |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Ornith JSON | 0/15 | 0/15 | 0 | 39 | 57207 / 5573 | 194,781 |
| Ornith native | 11/15 | 9/15 | 2 | 100 | 265326 / 17366 | 890,466 |
| Qwen2.5 JSON | 1/15 | 1/15 | 0 | 51 | 96608 / 4799 | 137,932 |

Ornith JSON часто выдаёт пояснение и JSON одновременно или task_stage metadata;
строгий decoder не выполняет такой текст как команду. Qwen также выдаёт примеры
команд и обещания вместо действий. Agent при этом иногда завершает цикл, хотя
независимый oracle не обнаруживает правку: `completed` нельзя считать приёмкой.

В native Ornith две правильные правки большого проекта остановлены на 10 turns
контрольного эксперимента: это верный код без наблюдённого E2E завершения.
Остальные четыре провала — неточная/отсутствующая строка определения/вызова.
Срезы времени не сравниваются как чистая скорость моделей: число действий и их
качество различаются. Usage присутствует для всех 190 POST этих трёх прогонов.

Отдельный поиск до индекса: малый проект p50 67–73 мс, средний 1527–1599 мс,
большой около 3000 мс и **truncated=time, Recall@10=0**. Для малого и среднего
Recall@10=1. Это ограничение линейного обхода, не повод объявлять символ отсутствующим.

Полные исходные отчёты, transcripts и snapshots находятся в:

- `.test-data/ornith-baseline-json-v1/`
- `.test-data/ornith-baseline-native-v1/`
- `.test-data/qwen25-baseline-json-v1/`
- сводка `.test-data/agent-baseline-20a-summary.json`

Agent/Core и requirements совпадают побайтно во всех трёх snapshots:
application digest `d87e2756af757a479305812f3e2c051236b150adf7a0c656fa5e16517523d598`.
Runner между прогонами уточнялся: provenance проверки, независимый oracle и
разделение task correctness/E2E; его отдельный hash сохранён в каждом snapshot.
Это ограничение прямой сопоставимости, а не скрытая смена production Agent.
Исходные JSON-отчёты не переписаны; человекочитаемые таблицы построены из них.

Измерительный gate 20a выполнен с указанными ограничениями. CPU/RAM profiling,
точный backend version и аварийное восстановление неизвестного эффекта остаются
долгом стенда; автоматическая приёмка качества приложения baseline не пройдена.

## Повтор запуска

В уже загруженной единственной модели LM Studio с известным API identifier:

```powershell
.\.venv-test\Scripts\python.exe tools/benchmark_agent.py `
  --out .test-data/my-fresh-baseline --model MODEL_ID --protocol json --live
```

Без `--live` создаются corpus, snapshot и search measurements; LLM status остаётся
pending. Без реально загруженного выбранного instance live-run отказывается от
работы и не загружает модель через JIT сам. Частичные результаты остаются на диске.
Для быстрого узкого прогона доступны `--sizes small` и `--cases definition bugfix`.

[Unit-тесты runner](../tests/test_agent_benchmark.py) проверяют владение каталогом,
reset без удаления чужих файлов, отрицательные AST-контракты, согласованность
multifile, запрет ложного успеха по угаданному пути/совпадению префикса номера строки
и строгую JSON-сериализацию. Девять тестов runner входят в итоговые 369 unit.

Следующий кодовый этап после baseline — [10 (JSON compatibility)](59-json-compatibility-stage10.md); первые реальные
данные указывают на необходимость строгого prompt/preset и bounded repair без
ослабления JSON decoder. Индекс 13a и ContextPack 14a ещё не объявлены выполненными.
