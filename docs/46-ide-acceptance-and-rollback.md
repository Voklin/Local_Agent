# Этап 6: критерии готовности, проверки и откат IDE

## Пользовательский сценарий

В IDE над вводом задачи появился сворачиваемый раздел **План и проверки**. Здесь
можно включить «Агент только читает и объясняет», перечислить критерии готовности,
добавить до восьми команд проверок и связать критерии с ними. Для каждой команды
задаются назначение, программа, аргументы по одному на строке, папка относительно
корня и лимит 1–120 секунд. Программа Node доступна из поставки приложения.

Опция **Предлагать запуск после правок** по умолчанию выключена. После включения
назначенные команды предлагаются после файловой работы агента перед завершением
задачи. Каждая использует обычный диалог подтверждения с назначением, программой,
argv и рабочей папкой. Отключённое расширение команд остаётся отключённым.

Кнопка **Запустить проверки без модели** создаёт отдельный запуск проверок в текущем
IDE-чате. Запроса к серверу модели нет. Сохраняются обычные stop, approval, journal,
exit code и task events. Для запуска нужно включённое расширение «Проверки и команды
проекта». Отказ в подтверждении не запускает программу. Команды могут менять файлы
и выполняются с правами пользователя; shell=False и подтверждения не являются
операционной изоляцией произвольного исполняемого кода.

В подробностях задачи отображаются конкретные предложенные шаги, критерии,
назначение команды, argv, код выхода и актуальность результатов. Успешная команда
подтверждает связанную проверку; творческие и другие непокрытые критерии остаются
с отметкой **Не подтверждено**. После новой файловой правки или отката прежние
результаты получают отметку **устарел**. Новый успех другой команды не стирает
непройденную проверку автоматически.

## План и ограничение чтения

[task_contract.py](../agent/task_contract.py) содержит `validate_options`,
`install_contract`, `set_plan`, `command_key` и `acceptance_summary`.

`validate_options` вызывается до очистки прежнего checkpoint и до вычислений.
Он проверяет boolean-флаги, до 12 пользовательских критериев по 500 символов,
до восьми проверок, уникальные IDs и корректные ссылки критериев. Программа,
argv, cwd, timeout и purpose имеют ограничения типа/длины. Пустая checks_only задача
и сочетание readonly с запуском программ отклоняются.

Внутренний инструмент `set_task_plan` позволяет модели сохранить до 12 шагов и
дополнительные критерии. Пользовательские критерии сохраняются, неизвестные check IDs
отклоняются. Инструмент не принимает поля «успех» или «проверено»: свидетельства
рассчитывает приложение. Модельный план дополняет прежние фазы analysis/research/
implementation/verification/finish, а не создаёт цепочку отдельных моделей.

Параметр `read_only` действует в [ToolPolicy/ToolExecutor](../agent/tool_executor.py).
Из payload исключаются mutators и внешние MCP schemas. Если модель всё равно
пришлёт запрещённый call, policy вернёт `READ_ONLY` до `started`, approval или
dispatch. Допускаются фиксированные читатели проекта, получение сохранённых
результатов и план как метаданные. Команды и неизвестные внешние инструменты
считаются эффектами независимо от деклараций MCP. Обновление памяти проекта
также отключается. Прямые ручные действия пользователя в редакторе остаются
отдельными действиями интерфейса.

Параметры сохраняются в `task.options`; при открытии IDE-чата форма восстанавливает
их из checkpoint. Пустые строки критериев удаляются с корректным перенумерованием
ссылок через `serializeIdeOptions`. При resume сохраняются исходные ограничения.

## Реальные свидетельства проверок

[StageVerifier](../agent/verifier.py) хранит `program`, `arguments`, `cwd`, `purpose`,
`exit_code`, `ok`, ID проверки и generation. `command_key` строится из точных
program/argv/cwd. `check_id` связывается с пользовательской проверкой только при
совпадении этой команды: одна метка, присланная моделью, не является свидетельством.

`workspace_generation` записывается в durable receipts файловых tools и команд.
Успешное изменение увеличивает generation; команда получает текущую generation.
`recover_task` воспроизводит эти значения из журнала, сохраняя привязку доказательств
к состоянию файлов. Результат на предыдущей generation становится stale. Методы
`refresh`/`acceptance_summary` пересчитывают проекции при загрузке и после отката.

| Состояние | Значение |
| --- | --- |
| `not_run` | Нет записанных командных свидетельств. |
| `failed` | Есть текущая команда с ненулевым exit code или неподтверждённым итогом. |
| `stale` | После команды изменилось состояние workspace. |
| `incomplete` | Не все назначенные проверки выполнены или часть критериев не покрыта. |
| `commands_passed` | Учтённые текущие команды успешны; summary сохраняет предел этого доказательства. |

Критерий имеет `unverified`, `failed`, `stale` или `checks_passed`. Непокрытые критерии
явно возвращаются в `verification.uncovered`. Завершение ответа модели не превращает
их в подтверждённые требования. При failed проверке задача приостанавливается.

`AgentEngine._run_configured_checks` использует те же ToolExecutor, CallJournal,
approval callbacks и ProcessJob, что обычная команда модели. Для checks_only не
создаётся ModelClient. При post-edit проверках команды добавляются в каноническую
историю вместе с assistant batch и tool receipts, поэтому сохраняются правила
crash/restart этапов [2](42-core-execution-and-recovery.md) и
[5](45-transactional-storage-and-migration.md).

## Снимки файловых правок

[workspace_snapshots.py](../agent/workspace_snapshots.py) хранит before/after для
`write_file`, `patch_file`, `rename_file`, `delete_file`, `create_directory`.

1. Пользователь просматривает обычный diff и подтверждает файловую операцию.
2. `ToolExecutor._capture_snapshot` сохраняет исходные bytes и запись `prepared`
   до durable `started`. Ошибка before-image блокирует сам эффект.
3. После операции `finish` сравнивает фактический результат с ожидаемым hash/видом
   пути. Только подтверждённый after получает статус `applied`.
4. Неожиданные post-edit bytes не присваиваются агенту как безопасно отменяемый
   результат: сохраняется unknown и действует обычное восстановление неизвестного
   эффекта. Потерянный after нельзя автоматически придумать при рестарте.

`SnapshotStore.capture` принимает обычные файлы до 1 МБ и реальные каталоги внутри
выбранного корня. Учитываются SHA-256, размер, filesystem identity, mtime, режим
доступа и identity родителя. Symlink/junction и `.git` через файловые изменения
снимков не обходятся. Снимки содержат только затронутые пути, не копию всего проекта.

Записи группируются в undo segments одной эпохи задачи. Первое before и последнее
after каждого пути образуют обратное изменение группы. Сегмент содержит до 80 путей.
Если между операциями пользователь отредактировал тот же файл, начинается новый
сегмент: его откат возвращает промежуточную ручную версию. Более ранний сегмент
откажется перезаписывать эту ручную ревизию. История не зависит от текущего checkpoint;
доступно до 50 последних групп выбранного чата/root.

Содержимое хранится в immutable artifacts как base64 исходных bytes под
`artifacts/workspace-snapshots/`. Используются существующие SHA-256/fsync/replace
примитивы ArtifactStore. Это позволяет точно вернуть CRLF и двоичные файлы при
обратном rename. Перед восстановлением проверяются artifact checksum, base64 и
исходный SHA-256. Пути и статусы возвращаются в UI без backup bytes.

## Compare → preview → confirm

В подробностях задачи появился раздел **Изменения и откат**. Кнопка **Сравнить и
отменить** получает обратный diff. До подтверждения файлы не меняются. Серверный
proposal привязан к chat/root/group/fingerprint, одноразовый и действует 120 секунд.
После **Подтвердить откат файлов** все ревизии проверяются повторно.

Откат откажется от работы, если изменился root identity, файл, родитель, тип пути
либо появилась новая запись внутри созданной папки. Если конфликт обнаружен до
первого эффекта, ни один файл группы не меняется. Перед каждым следующим эффектом
ревизия проверяется ещё раз. Созданные файлы удаляются, исходные восстанавливаются
через temp/fsync/replace, новые папки удаляются только пустыми. Права файлов
восстанавливаются вместе с bytes; прежняя filesystem identity и mtime не воссоздаются.

Несохранённые правки редактора блокируют действия отката в UI. После успешного
восстановления обновляются редактор, каталог и чат. Долговечная rollback revision
инвалидирует старые проверки даже при аварии до обновления task/chat проекции.
В канонической истории сохраняется сообщение о действии пользователя: последующая
модель видит факт отката и должна проверять актуальные файлы.

Панель подробностей имеет общую ограниченную прокрутку: управление откатом доступно
и при длинном журнале. Закрытие панели по X/Esc/внешнему клику сохраняет прежнее
поведение и не отменяет исполняемую задачу.

## Прерванный откат и пределы восстановления

Операции над несколькими файлами не образуют одну атомарную filesystem-транзакцию.
До первого эффекта фиксируются `rolling_back` и новая revision. После каждого пути
сохраняется прогресс. При ошибке остаётся `rollback_unknown`; после настоящего
process exit может остаться `rolling_back`. Оба состояния блокируют новый запуск
этого IDE-чата. При повторном открытии эффекты автоматически не воспроизводятся.

Пользователь должен проверить перечисленные файлы и выбрать **Я проверил файлы
вручную**, затем подтвердить наблюдение. Запись становится `abandoned`; файлы не
меняются. UI показывает «Файлы проверены вручную», а не обещает полный откат.
Незавершённый tool effect и прерванный rollback имеют собственные recovery gates:
подтверждение одного не подменяет проверку другого.

Снимки покрывают только перечисленные файловые инструменты. Произвольные команды,
MCP, браузер, Telegram, музыка и внешние эффекты не отменяются этим механизмом.
Ручная правка и команды, изменившие затронутые файлы, приводят к конфликту ревизий.
Проверки в этом этапе не доказывают отсутствие всех ошибок и не оценивают качество
визуального дизайна автоматически. Физическое отключение питания и аппаратные
сбои диска не воспроизводились; проверены process exit, отказ записи и конфликты.

## SQLite v2 и резервная копия

Схема [Storage](../agent/storage.py) увеличена до 2. Миграция из v1 одной транзакцией
добавляет `workspace_snapshots` и индекс по chat/root/group/sequence, сохраняя
канонические чаты, сообщения, проекты и receipts. Исходная JSON migration остаётся
версии 1 и повторно не выполняется. Старый stage5 installer не должен открывать
новую v2 базу; он корректно отклоняет более новую схему.

`workspace_snapshots` хранит id/group/chat/journal/root/status/data, прогресс, ошибку
отката и revision. Последняя revision читается даже если событие ещё не попало в
task projection. Таблица не является snapshot всего произвольного терминального
сеанса. Удаление чата удаляет и его snapshot metadata. Immutable artifacts пока
не собираются автоматически.

Резервная ZIP-копия из настроек включает необходимые snapshot artifacts вместе с
SQLite online snapshot. Восстановление по-прежнему выполняется при закрытом Neutral
в пустой профиль; смешивание живого WAL и чужой базы не поддерживается.
