# Проверяемая область команды перед Project Intelligence

27 октября 2026. Предварительный контракт этапов 13a/14a из
[Roadmap V2](57-roadmap-v2.md). Это отдельная поставка evidence; индекс, watcher,
ContextPack и субагенты ещё не подключены. Установщик не собирается.

## Проблема и поведение

Раньше любой exit=0 требовал полного fingerprint проекта. Посторонний файл размером
8 000 001 байт делал даже успешную проверку синтаксиса одного файла `stale`.
Убирать эту защиту для произвольных команд нельзя: мы не знаем их зависимостей.

Теперь отдельно сохраняются:

- факт исполнения команды: outcome, exit code, время, hash её параметров;
- область доказательств: весь проект либо явно выбранные пользователем файлы;
- снимки **до и после** исполнения, их стабильность и актуальность сейчас;
- полнота покрытия проекта. Scoped success всегда имеет `project_complete=false`.

Произвольная команда модели по умолчанию проверяется по всему проекту.
Если fingerprint неполный, exit=0 сохраняется как успешное исполнение, а актуальность
исходников остаётся неподтверждённой. Такая проверка не становится зелёным успехом.

Пользовательская проверка с явно заданными файлами может получить `scoped_passed`.
В интерфейсе это «Проверены выбранные файлы» и сообщение «Остальной проект не
сверялся». Такой результат позволяет закончить задачу с явным ограничением покрытия.
Связанный критерий получает `scoped_checks_passed`, отдельно от полного `checks_passed`.

## Настройка в IDE

Откройте «План и проверки», добавьте команду и выберите «Область подтверждения»:

1. **Весь проект** — существующая строгая сверка source tree, с её прежними исключениями
   `.git`, node_modules, build/dist, кешей и виртуальных окружений.
2. **Выбранные файлы и зависимости** — точные относительные пути сохранённых файлов,
   по одному на строке. Отдельно укажите тесты, настройки, импортируемые исходники
   и другие известные зависимости проверки.

Список зависимостей — декларация пользователя, а не результат доказанного анализа
транзитивного графа. Неизвестная/забытая зависимость не даёт права заявлять, что
проверен весь проект. Glob, директории, абсолютные пути, переходы `..` и ADS не
принимаются. Пустые строки UI удаляются при сериализации. Файлы должны существовать
и быть доступны текущей WorkspaceAccessPolicy.

Перед запуском обычное approval показывает программу, argv, cwd и эту область.
**Область доказательств не ограничивает доступ запускаемой программы.** Прежние
правила включения команд, отдельное подтверждение, no-shell и управление процессами
остаются. Scope не является файловой песочницей и не предоставляет новых прав модели.

### Version 2 receipt

`verification_receipt` находится в обычном результате run_project_command, затем
в CallJournal, tool message и проекции `test_results`:

```text
version: 2
command_hash: SHA-256(program, arguments, cwd, timeout, scope)
scope: workspace | files + dependencies
execution: outcome, exit_code, started_at, finished_at, elapsed_ms
witness: before, after
rollback_revision, generation
```

Модель не передаёт scope через schema run_project_command. Только совпадение
пользовательских check_id, argv, cwd, program и timeout разрешает наследовать
scope из options. При другом вызове используется workspace. Изменение options
или списка зависимостей инвалидирует прежний receipt. Назначение команды — label,
а не её identity.

Снимки связаны с canonical workspace id, содержимым, revision version/scope.
Для scoped файлов дополнительно учитывается версия правил доступа. Изменение
scope-файла, зависимости, `.neutralignore`, отзыв разрешения, отсутствие файла,
смена workspace и нестабильное чтение не дают успешной актуальности. Проверяется
и policy после чтения. Символьные ссылки/junction не входят в file scope.

Если команда меняет покрываемые исходники, before/after различаются: exit=0
сохраняется, но tested snapshot не считается стабильным. Повторите проверку после
окончания записи. Это оптимистическая проверка снимков, а не блокировка файловой
системы на весь период исполнения; изменение и возврат байтов между наблюдениями
не является покрытым сценарием.

Вне scoped списка обычная правка не инвалидирует его доказательства. При откате
используется отдельная observed rollback revision: возвращение прежних байтов не
делает старый результат снова свежим. Полный workspace scope также сохраняет
прежнюю консервативную проверку workspace_generation.

capture_files ограничен до 256 точных путей, 8 МБ на файл, 96 МБ суммарного чтения
и 2 секундами. Это границы одного capture, а не новые глобальные лимиты локальной
агентской задачи. Превышение оставляет evidence неподтверждённым. Успешный маленький
scope не требует полного scan большого проекта.

Hash команды описывает заявленную конфигурацию, не все свойства runtime: смена
интерпретатора, окружения, внешнего сервиса или содержимого зависимостей вне
объявленной области этой поставкой автоматически не доказывается.

### Старые данные

Checkpoint помечается `verification_schema=2`. Старые результаты без v2 witness
становятся `unverified`, даже если ранее имели полный v1 fingerprint и exit=0.
Код выхода и история сохраняются, исходная квитанция журнала не переписывается.
Миграция проекции выполняется лениво при чтении checkpoint; сохранение происходит
обычным путём следующего checkpoint. SQL schema не меняется, второй журнал не создаётся.
Recovery повторно оценивает durable receipt без повторного запуска программы.
