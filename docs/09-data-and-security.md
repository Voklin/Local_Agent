# 9. Хранилища, файлы и разрешения

## Раздельные данные

Рабочая папка содержит исходники пользователя. Служебные хранилища приложения обычно располагаются в `%LOCALAPPDATA%\LocalCodingAgent`. Резервные пути при отсутствии `LOCALAPPDATA` отличаются по модулям: большинство stores использует домашний `AppData/Local`, а `model_manager.py` — `~/.local`. Это следует учитывать при переносе на другую ОС.

| Данные | Расположение | Назначение |
| --- | --- | --- |
| Индекс чатов | `chats/index.json` | Восстанавливаемый кэш метаданных, не источник истины |
| Диалог | `chats/<uuid>.json` | Канонические сообщения, embedded checkpoint, draft, проект и метаданные |
| Задача | `tasks/<hash>.json` | Этап, статус, счётчики и resume state |
| Память | `project_memory/<hash>/memory.json` | Структурированные краткие сведения о проекте |
| Настройки модели | `model-preferences.json` | `base_url`, `model`, whitelist числовых `settings` для Electron Core; без ключа |
| GGUF и runtime | `models/`, `runtime/` | Используются сохранённым менеджером локальных моделей |
| Qt preferences | `QSettings` | Отдельные настройки сохранённого GUI, включая ключ из старого диалога |

Константы путей вычисляются при импорте модулей. Если тест меняет `LOCALAPPDATA` после импорта, уже созданные `Path` не пересчитаются автоматически. Поэтому тесты также подменяют константы через `patch`.

## Структура чата

```json
{
  "id": "0123456789abcdef0123456789abcdef",
  "title": "Изучить обработку настроек",
  "created_at": "2026-10-22T10:00:00+00:00",
  "updated_at": "2026-10-22T10:01:00+00:00",
  "project_root": "C:\\Projects\\example",
  "model": "example-model",
  "messages": [
    {"role": "user", "content": "Объясни структуру"},
    {"role": "assistant", "content": "Начну с файлов проекта"}
  ]
}
```

Реальный список может содержать assistant tool calls и tool results с текстом файлов. Следовательно, сохранённый чат потенциально содержит прочитанный исходный код. Фраза «checkpoint не хранит сырые tool outputs» не распространяется на историю диалога. При передаче служебной папки другому человеку это различие важно.

`save_chat` выполняет flush/fsync временного JSON и атомарную замену канонического файла. Ошибка перед заменой оставляет прошлую запись. Индекс обновляется отдельно и является кэшем: его отказ возвращается предупреждением, а уже сохранённая история не отменяется. `read_chat_catalog` читает канонические JSON и пересоздаёт метаданные; отсутствие/повреждение/устаревание индекса не скрывает валидные чаты. Повреждённые файлы чатов остаются нетронутыми, список показывает остальные и предупреждает о конкретном ID.

Каталог читает полные записи для восстановления метаданных. На большой библиотеке длинных чатов это может быть дорого; ускоряющий индекс с проверяемой актуальностью или БД — отдельная оптимизация. Нет общей транзакции с файлами проекта, гарантии против любой потери питания или блокировки второго экземпляра приложения.

## Поля восстановления Electron

Существующий JSON остаётся совместимым: следующие поля опциональны, старые чаты читаются без миграции.

| Поле | Смысл |
| --- | --- |
| `active_run_id` | Запуск, которому принадлежит текущий draft |
| `task_checkpoint` | Снимок task в том же атомарном файле, что и messages; источник восстановления для Electron |
| `stream_draft` | `run_id`, `turn`, `text`: первый фрагмент сохраняется до UI-события, последующие — максимум примерно раз в секунду, включая паузу сервера |
| `recovery_fragments` | Неотнесённые/некорректные draft сохраняются отдельно, не смешиваясь автоматически с диалогом |

При открытии незавершённый запуск становится paused. Draft текущего run добавляется к transcript один раз и удаляется из отдельного поля. Устаревшее согласие не восстанавливается. Из embedded checkpoint восстанавливается отдельный tasks-файл; старые чаты без embedded поля используют прежний tasks-файл.

Для записи checkpoint содержит `pending_write`: относительный путь, call ID, индекс assistant-сообщения, состояние awaiting_approval/applying и snapshot хешей. В journal нет предлагаемого полного текста или API-ключа. Если после сбоя в соответствующем блоке сообщений уже есть результат инструмента, учитывается именно он. Старый результат с таким же call ID из другого хода не подходит. Если запись могла выполниться, но результат не сохранён, UI требует проверить файл; приложение не повторяет запись автоматически. При явном resume предупреждение переносится в resume_state.recovery_note, а next_action напоминает модели проверить состояние.

Граница сохранения потока — периодический снимок, поэтому при жёстком kill возможна потеря самого нового фрагмента за интервал до следующего сохранения. Между заменой файла проекта и записью результата инструмента остаётся зона неопределённости, отражаемая предупреждением, а не ложным утверждением об успехе.

## Структура задачи

Checkpoint включает `version: 2`, `runtime_version`, `chat_id`, `project_root`, исходный `prompt`, `status`, `stage`, `turn`, `tool_calls`, даты, массив `stages` и `resume_state`.

`status` в активном сценарии — `running`, `paused`, `completed`. `stage` может быть `analysis`, `research`, `implementation`, `verification`, `finish`; набор зависит от плана. В новых запусках `modified_files` пополняется только после успешного `write_file`; предложения, отказы и конфликты туда не добавляются. Старые сохранённые checkpoint могут содержать записи по прежней логике и автоматически не пересчитываются. Для точного разбора используйте также `change.status` и сохранённые tool results.

`test_results` предусмотрено форматом, но текущие четыре tools не умеют запускать тесты. Наличие поля не является доказательством выполненных проверок.

## Память проекта

`project_memory.py` ограничивает строки `project_summary`, `current_focus`, `next_steps` и списки решений, ограничений, соглашений и важных файлов. `validate_memory` нормализует типы, длины и дубликаты. `merge_memory_update` сохраняет существующие поля, которых не было в обновлении.

Модель получает для обновления памяти краткий prompt, итоговую сводку, метаданные инструментов и прежнюю память. Это сокращает перенос данных, но не является формальным доказательством отсутствия любых секретов: пользователь или модель могут включить их в краткий текст. `format_memory_context` помечает память как справочную информацию, а не источник новых разрешений.

## Настройки модели

`save_preferences` создаёт новый словарь только из разрешённых полей. Ключ и любые дополнительные поля отбрасываются. URL должен быть HTTP(S), без user/password, query и fragment, с корректным портом. Повреждённый файл приводит к значениям по умолчанию.

Это локальный JSON, не credential store. В Electron ключ остаётся в памяти процесса; в старом Qt-диалоге отдельный `QSettings` хранит его иначе. Документация не объединяет эти два режима в одну гарантию.

## Защита путей

`canonical_root` требует существующий каталог. `resolve_allowed_path` раскрывает `~`, делает абсолютный путь, разрешает ссылки и проверяет, что результат находится внутри канонического корня. Абсолютный путь принимается только если он остаётся внутри проекта.

Таким образом, строка `../outside.txt` и ссылка из проекта во внешний каталог должны быть отклонены. Это проверяется тестами. На Windows тест создания symlink может быть пропущен, если у окружения нет соответствующего разрешения; такой пропуск не означает успешную проверку symlink-сценария на этой машине.

Bridge использует собственный `resolve_inside` для UI-операций. Файловые инструменты используют `security.resolve_allowed_path`. Две реализации служат разным поверхностям; менять одну и забывать другую опасно для согласованности.

## Лимиты файлов

| Операция | Ограничение текущего кода |
| --- | --- |
| `tools.read_file` | 120 000 байт |
| Preview существующего файла перед заменой | 120 000 байт |
| Новое содержимое при preview/write | 1 000 000 байт UTF-8 |
| `bridge.read_file` | 1 000 000 байт |
| `editor_io.read_project_text` | 2 × 1024 × 1024 байт |
| Qt-предпросмотр | 2 × 1024 × 1024 байт |
| Поиск инструмента | До 200 совпадений, 500 символов текста на совпадение |

Bridge отбирает первые 1000 кандидатов каталога до части фильтров; `truncated` вычисляется по числу добавленных элементов. Поэтому этот флаг не является строгим доказательством полноты/неполноты при большом количестве игнорируемых или отклонённых записей.

## Границы гарантий

Python-проверка путей — sandbox уровня приложения, не ОС-контейнер. Electron sandbox относится к renderer, а не изоляции Python от всех файлов компьютера. Файловая запись повторно проверяет путь, однако несколько отдельных операций проверки не равны защите от любого конкурентного изменения файловой системы.

Согласие связано со снимком исходных байтов, пути и предлагаемого текста. Перед записью и после подготовки временного файла движок повторно сверяет снимок; изменившийся/удалённый/созданный target требует нового diff. Новые файлы создаются операцией, которая не заменяет уже появившийся target. Для существующего файла между последней проверкой и `os.replace` остаётся короткое окно конкурентной правки: это обнаружение конфликтов на контрольных точках, а не универсальная файловая транзакция/блокировка всех внешних редакторов. Также повторные проверки путей не устраняют все возможные гонки с перенаправлением каталогов.

Скрытие `.git` или `node_modules` из списка — удобство обхода, а не общий запрет чтения любого скрытого файла внутри корня. Читайте выбранный корень как реальную область доступа агента и не приписывайте списку исключений роль полноценной политики секретов.

## Обновление трёх режимов

Chat работает без папки в области `project_root=""` с отключёнными tools и проектной памятью. IDE сохраняет прежнюю работу с выбранным корнем. Для RPC истории и старта добавлен необязательный `mode=chat|ide` (по умолчанию ide). Ассистент пока представляет подготовительный экран без аудио. Подробности архитектуры, IPC, восстановления пустых ответов и границ реализации — в [главе 16](16-workspaces-and-answer-recovery.md).
