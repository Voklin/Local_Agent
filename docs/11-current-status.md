# 11. Реальный статус и технический долг

Эта глава нужна, чтобы учебный материал не описывал запланированные функции как готовые. Она фиксирует наблюдения по коду, а не требует немедленно менять все перечисленные части.

## Что работает в активном Electron-пути

Редактор проекта с вкладками и snapshot Save, поиск/Ctrl+P, настройки модели и собственный GGUF runtime, цикл четырёх файловых инструментов, diff approval, история/rename, редактор компактной памяти, checkpoint/resume, потоковый текст и отмена сетевого запроса. Мия имеет отдельный mode/history/model, настраиваемый характер, Windows TTS и микрофон с STT через настроенный whisper.cpp/совместимый endpoint. URL и модель сохраняются без API-ключа. Windows-тесты и сборка автоматизированы; отдельный UI smoke проходит локально.

## Что существует отдельно

| Компонент | Фактический статус |
| --- | --- |
| `MCPRegistry` | Хранит конфигурации; не реализует MCP transport и исполнение tools |
| `SkillManager.load` | Умеет читать полный навык; engine использует выбранные краткие описания |
| `TaskPlanner`, `StageVerifier` | Примитивы доступны; полный планировщик с обязательной проверкой каждого этапа не подключён |
| `ModelManager`, `LocalRuntime`, `ModelGateway` | LocalRuntime подключён к Electron через RuntimeService; scan/import ModelManager и ModelGateway остаются отдельными legacy abstractions |
| `editor_io` | Старые отдельные функции; Electron теперь использует EditorService с revisions/approval, а не этот legacy save |
| `design_reference` | Эталон внешнего вида с собственными механизмами; не runtime приложения |
| Windows packaging | Есть frozen Core, NSIS config и локальные smoke-проверки; приёмка install/upgrade/uninstall на чистой VM ещё не выполнена |

## Контекст и полнота истории

Каноническая история отделена от ограниченного контекста модели. Существующие чаты читаются без миграции; `build_messages` сохраняет все старые сообщения, а оба runtime-пути используют общий builder целых tool-пар. Сокращение не перезаписывает архив. Незавершённые tool-пары после остановки сохраняются в истории, но исключаются из следующего HTTP-запроса.

JSON-бюджет включает сериализацию списка messages, но не tools/прочие поля HTTP payload и не токены модели. Слишком большие обязательные данные приводят к явной ошибке до HTTP. Сообщения и embedded checkpoint сохраняются одним атомарным JSON. Индекс и отдельный task-файл восстанавливаются из него; первый и периодический stream draft переживают kill процесса. Граница между записью файла проекта и сохранением результата всё ещё требует предупреждения и ручной проверки при неопределённом исходе.

## План и результаты

Переходы в текущем run отражают анализ, реальные чтения/поиски (research), предложения записи (implementation), ответ/модельную проверку и завершение. Непосещённые этапы skipped. Поля `max_turns` отдельных `PlanStage` не превращаются автоматически в исполняемые ограничения каждого этапа. `StageVerifier` сам не запускает тесты. В системе нет shell tool, значит фраза в плане «запустить проверки» не означает наличие такой возможности у модели.

`modified_files` в новых запусках содержит только успешные записи; старые checkpoint могут содержать отклонённые предложения по прежней логике. Отдельные массивы checkpoint пока шире фактического заполнения. Не используйте их без проверки как журнал применённых изменений или отчёт о тестировании.

## Разрешения и данные

Preview связан с хешем исходных байтов и предложения; при несовпадении запись отменяется. У существующего файла остаётся окно между последней проверкой и атомарной заменой; проверки путей и хеша не дают универсальной межпроцессной compare-and-swap гарантии. Чаты содержат модельные сообщения и tool outputs; JSON не шифруется. Большинство служебных chat/task stores пока не имеют отдельного жёсткого read limit. Manual memory API ограничивает JSON 200 КБ, editor — 1 МБ.

Список игнорируемых каталогов не запрещает всякое чтение скрытых файлов по прямому пути внутри корня. Нет общего secret scanner. Текст исходников и ответов нужно рассматривать как данные для модели, а не источник полномочий на дополнительные инструменты.

## Сохранённый Qt-интерфейс

У Qt отдельное хранение настроек с сохранением ключа в `QSettings`, исходный проект по умолчанию может указывать на домашнюю папку. `start_agent` сохраняет user prompt локально, но передаёт движку историю до него; повторное добавление одного и того же запроса исправлено.

Qt-адаптер поддерживает событие `text_delta`, но `MainWindow` его не использует для постепенной отрисовки. Поэтому новая streaming UX относится к Electron. Qt-интерфейс сохранён для совместимости, а не является точной копией нового UI.

`run.bat` ссылается на отсутствующий `.env.example`; `python-dotenv` присутствует в полном списке зависимостей, но активный `main.py` его не использует. Документация не предлагает создавать выдуманные настройки `.env`, которые код не читает.

## Эксплуатационные ограничения

Остановка закрывает клиентский HTTP-запрос; поведение сервера после отключения зависит от его реализации. `list_models` теперь выполняется в отдельном worker с общим 5-секундным deadline и отменой; новые команды bridge не ждут ответа сервера. Перезапуск Python очищает состояние процесса и требует повторного выбора проекта.

Индекс — восстанавливаемый кэш; каталог сканирует канонические записи, что может замедляться на большой истории. Не предусмотрены миграции большой базы, архив всех логов, общая транзакция с несколькими файлами проекта и защита от одновременной записи одного чата двумя экземплярами. NSIS собирается локально; его install/upgrade/uninstall ещё требует приёмки на чистой Windows. Main diagnostic ограничен примерно 1 МБ.

## Приоритеты дальнейшей разработки

Текущий этап — проверка Windows-сборки и приёмка на чистой машине; конфигурация упаковки и локальный NSIS уже подготовлены. Базовое восстановление после сбоев реализовано и проверяется реальным kill тестового subprocess; обнаружение моделей вынесено из JSON-lines обработчика. Approval уже связан со снимком файла, а конфликты проверяются в unit, HTTP integration и настоящем Electron UI smoke. Каноническая история и общий context builder уже исправлены; дальнейшая очередь описана в WORK_PLAN.md. После этого — упаковка Windows с Python, отдельные UI-компоненты, типизированные события вместо `any`, credential store при необходимости. MCP transport и терминал требуют самостоятельного проектирования, а не включения одной кнопки.

## Поочерёдное обновление ядра и оболочки

Добавлена панель плана и журнала инструментов, сохраняемая через checkpoint. Это прозрачное отображение существующего цикла, а не полноценный интеллектуальный planner/verifier. Исходы tools подтверждаются их фактическими результатами; после сбоя запись без сохранённого результата требует проверки файла. См. [главу 15](15-task-progress.md).

## Обновление трёх режимов

Chat работает без папки в области `project_root=""` с отключёнными tools и проектной памятью. IDE сохраняет прежнюю работу с выбранным корнем. Для RPC истории и старта добавлен необязательный `mode=chat|ide|voice` (по умолчанию ide). Ассистент использует отдельный mode=voice, независимую модель и настраиваемую persona; есть системный TTS и явная запись микрофона через настраиваемый STT endpoint. Подробности архитектуры, IPC, восстановления пустых ответов и границ реализации — в [главе 16](16-workspaces-and-answer-recovery.md).

Модель настраивается в отдельном окне: URL/ключ/ID, draft discovery/probe, семь применяемых числовых параметров и явные результаты. Настройки сервера/GPU и системное хранилище ключа сюда не входят. Цвета IDE приведены к общей теме; подробности — [глава 17](17-model-settings-and-theme.md).
