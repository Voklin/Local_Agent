# 11. Реальный статус и технический долг

Эта глава нужна, чтобы учебный материал не описывал запланированные функции как готовые. Она фиксирует наблюдения по коду, а не требует немедленно менять все перечисленные части.

## Что работает в активном Electron-пути

Проект/предпросмотр, настройки модели, список моделей, цикл четырёх файловых инструментов, diff approval, история, компактная память, checkpoint/resume, потоковый текст и отмена сетевого запроса. URL и модель сохраняются без API-ключа. Windows-тесты и сборка автоматизированы; отдельный UI smoke проходит локально.

## Что существует отдельно

| Компонент | Фактический статус |
| --- | --- |
| `MCPRegistry` | Хранит конфигурации; не реализует MCP transport и исполнение tools |
| `SkillManager.load` | Умеет читать полный навык; engine использует выбранные краткие описания |
| `TaskPlanner`, `StageVerifier` | Примитивы доступны; полный планировщик с обязательной проверкой каждого этапа не подключён |
| `ModelManager`, `LocalRuntime`, `ModelGateway` | Реализованы отдельно; интерфейс Electron ими не управляет |
| `editor_io` | Самостоятельные функции чтения/сохранения; React preview не вызывает сохранение |
| `design_reference` | Эталон внешнего вида с собственными механизмами; не runtime приложения |
| Ветка `app.isPackaged` | Учитывает пути packaged-режима; готовой конфигурации упаковки Python нет |

## Контекст и полнота истории

Каноническая история отделена от ограниченного контекста модели. Существующие чаты читаются без миграции; `build_messages` сохраняет все старые сообщения, а оба runtime-пути используют общий builder целых tool-пар. Сокращение не перезаписывает архив. Незавершённые tool-пары после остановки сохраняются в истории, но исключаются из следующего HTTP-запроса.

JSON-бюджет включает сериализацию списка messages, но не tools/прочие поля HTTP payload и не токены модели. Слишком большие обязательные данные приводят к явной ошибке до HTTP. Снимки истории сохраняются на шагах движка, но гарантия crash-safe транзакций чата/индекса/checkpoint остаётся отдельной задачей.

## План и результаты

Переходы в текущем `run` в основном обновляют анализ, проверку и завершение. Поля `max_turns` отдельных `PlanStage` не превращаются автоматически в исполняемые ограничения каждого этапа. `StageVerifier` сам не запускает тесты. В системе нет shell tool, значит фраза в плане «запустить проверки» не означает наличие такой возможности у модели.

`modified_files` в новых запусках содержит только успешные записи; старые checkpoint могут содержать отклонённые предложения по прежней логике. Отдельные массивы checkpoint пока шире фактического заполнения. Не используйте их без проверки как журнал применённых изменений или отчёт о тестировании.

## Разрешения и данные

Preview связан с хешем исходных байтов и предложения; при несовпадении запись отменяется. У существующего файла остаётся окно между последней проверкой и атомарной заменой; проверки путей и хеша не дают универсальной межпроцессной compare-and-swap гарантии. Чаты содержат модельные сообщения и tool outputs; JSON не шифруется. Размер служебных файлов при чтении stores отдельно жёстко не ограничен.

Список игнорируемых каталогов не запрещает всякое чтение скрытых файлов по прямому пути внутри корня. Нет общего secret scanner. Текст исходников и ответов нужно рассматривать как данные для модели, а не источник полномочий на дополнительные инструменты.

## Сохранённый Qt-интерфейс

У Qt отдельное хранение настроек с сохранением ключа в `QSettings`, исходный проект по умолчанию может указывать на домашнюю папку. `start_agent` сохраняет user prompt локально, но передаёт движку историю до него; повторное добавление одного и того же запроса исправлено.

Qt-адаптер поддерживает событие `text_delta`, но `MainWindow` его не использует для постепенной отрисовки. Поэтому новая streaming UX относится к Electron. Qt-интерфейс сохранён для совместимости, а не является точной копией нового UI.

`run.bat` ссылается на отсутствующий `.env.example`; `python-dotenv` присутствует в полном списке зависимостей, но активный `main.py` его не использует. Документация не предлагает создавать выдуманные настройки `.env`, которые код не читает.

## Эксплуатационные ограничения

Остановка закрывает клиентский HTTP-запрос; поведение сервера после отключения зависит от его реализации. `list_models` пока синхронно занимает обработчик моста до своего timeout. Перезапуск Python очищает состояние процесса и требует повторного выбора проекта.

Между обновлением файла чата и индекса нет общей транзакции. Не предусмотрены миграции большой базы, автоматическая ротация логов, crash-safe транзакции нескольких файлов или установщик Windows.

## Приоритеты дальнейшей разработки

Следующий приоритет — отзывчивое обнаружение моделей и восстановление состояния после сбоев. Approval уже связан со снимком файла, а конфликты проверяются в unit, HTTP integration и настоящем Electron UI smoke. Каноническая история и общий context builder уже исправлены; дальнейшая очередь описана в WORK_PLAN.md. После этого — упаковка Windows с Python, отдельные UI-компоненты, типизированные события вместо `any`, credential store при необходимости. MCP transport и терминал требуют самостоятельного проектирования, а не включения одной кнопки.
