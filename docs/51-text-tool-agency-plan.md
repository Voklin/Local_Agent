# План агентской работы моделей без native tool calling

Сейчас JSON adapter уже переводит tools в текст и использует обычный ToolExecutor/
approval/journal. Сохраняем этот путь исполнения. Улучшаем распознавание намерения,
ограничение контекста, обратную связь и измерение качества; модель не становится
эквивалентной хорошо обученной native-tool модели только за счёт парсера.

## 1. Контракт ответа

Предлагаемый strict протокол v1 различает действие и финальный текст:

```json
{"protocol":"neutral.action.v1","kind":"tool","name":"read_range","arguments":{"path":"src/main.py","start_line":1,"end_line":80}}
```

```json
{"protocol":"neutral.action.v1","kind":"final","text":"Итог работы…"}
```

Обрабатывается ровно один полный JSON object, без trailing prose, второго объекта,
дублирующих ключей, извлечения из рассуждений или Markdown-примеров. Call ID выдаёт
host и сохраняет в journal. Для слабых моделей можно явно включить совместимый
финальный plain-text ответ; action envelope остаётся недвусмысленным. Старый режим
не менять молча: отдельный compatibility preset и миграция с объяснением.

Текст из файлов/tool results, в том числе похожий на action, никогда не поступает
в parser как новый assistant response. Tools разрешаются из эффективного capability
snapshot; complete JSON не обходит readonly, schema, scope, approval и revision.

## 2. Поток и завершение

Ввести общий результат ModelAdapter: outcome, text, normalized calls, finish_reason,
usage, provider/model capability profile. Native и JSON завершаются одинаково.
EOF без terminal status, length/refusal/filter, timeout и повреждённый JSON сохраняют
частичный ответ, но не разрешают action и не становятся зелёным completed.

Incremental parser нужен для прогресса «модель готовит действие», а не для раннего
запуска команды. Effect начинается только после полного validation и terminal
completion. Предел измерять UTF-8 байтами; отдельный небольшой action cap, например
64 КБ. Финальный текст можно показывать постепенно без утечки служебного JSON в TTS.
Большие изменения лучше передавать patch_file с anchors, а не мегабайтами write_file.

## 3. Меньше схем и понятная обратная связь

На шаг выдавать небольшой выбранный набор tools: поиск/чтение, редактирование,
проверки, делегирование. Остальные доступны через каталог по запросу. Общий
RequestBudget после преобразования остаётся обязательным. Примеры должны содержать
настоящие required arguments; текущий универсальный пример с пустым `{}` недостаточен.

ToolResult имеет code, краткую сводку, данные/артефакт и следующий допустимый шаг:
INVALID_ARGUMENTS, USER_DENIED, STALE_REVISION, OUTCOME_UNKNOWN. Ошибка не превращается
в успешный ответ, отказ не вызывает бесконечное повторное согласование. В первой
версии один effectful action за ответ, небольшой batch — только для независимого чтения.

Сохранить уже имеющееся преобразование native history в обычные chat messages:
не отправлять `tools`/`tool_choice` и роль `tool` серверу без этой поддержки. В новом
протоколе предыдущий action и связанный по host ID результат сериализуются отдельными
помеченными блоками данных; выбранный chat template должен поддерживать полученную
последовательность ролей. Каноническая история в store остаётся нормализованной,
а преобразование выполняет только adapter перед запросом. Бюджет считается после
такой сериализации. Добавить fixtures серверов, отклоняющих native tool fields и роли.

## 4. Восстановление формата и защита от циклов

Синтаксическая ошибка: не выполнять действие, показать модели конкретную ошибку
и допустимую schema. Один bounded repair request по умолчанию; он расходует общий
root budget. Нельзя угадывать путь, overwrite, аргументы shell или добавлять права.
Локально разрешены только заранее описанные безопасные нормализации whitespace;
додумывание незакрытого action не является безопасной нормализацией.

Повтор той же команды после committed receipt не исполняется автоматически.
Идентичный запрос чтения с новой revision может быть допустим; одинаковый текст
действия не означает одинаковую авторизацию. UNKNOWN effect требует recovery UI.
Модель получает краткую память об отказах/результатах и ссылку на полный artifact.

## 5. Профили моделей и UI

В настройках соединения: «Нативные инструменты», «JSON действия», «Только разговор»;
рядом тест протокола с понятным результатом. Для Qwen2.5-Coder предусмотреть preset
коротких schemas, низкой температуры и ограниченного output. Не назначать один
параметр оптимальным для всех quantizations/context sizes без измерения.

Constrained JSON/schema generation включать только если выбранный сервер реально
поддерживает её; не посылать несуществующий универсальный grammar API. В рамках
бюджета разрешить явную диагностику capability. На совместимых серверах schema
ограничивает формат, а семантика/права всё равно проверяются host.

UI показывает выбранный протокол, ожидание, исправление формата 1/1, ошибку модели
и сохранённый прогресс. Пользователь не обязан писать JSON. У Лолы очищается только
произносимый ответ; JSON action и результаты программ не проговариваются.

## 6. Приёмочная матрица

Фиксированный corpus: поиск → read_range → patch → проверка, пользовательский отказ,
неизвестный tool, неверные типы, русский Unicode, 4K/8K контекст, два JSON объекта,
примеры в коде, duplicate keys, streaming EOF, cancellation, restart и prompt injection
в результате. Измерять valid-action rate, repair success, ошибочные исполнения (цель 0),
завершённые критерии, HTTP attempts, reported tokens и p50/p95 времени.

Сначала deterministic fixtures, затем по одному реальному запуску выбранных моделей
с безопасными GPU настройками. Не менять параметры загрузки LM Studio автоматически
и не запускать несколько тяжёлых inference. Профиль признаётся рабочим по измеренным
сценариям, а не по одному красивому ответу. Новые parser cases из главы 49 должны
стать regression tests до подключения spawn_agent к JSON протоколу.
