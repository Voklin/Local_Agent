## 0. Решение по аудиту Sol

**Принять исходный план с обязательными поправками.** Первый пользовательски полезный результат: *запрос о большом проекте → точный поиск файла/символа → ограниченный проверяемый контекст → небольшая правка → тест → объяснение результата*. Этот путь не требует субагентов или embeddings.

Три обязательных архитектурных инварианта:

1. **Инкрементальное обновление без полного сканирования при штатных изменениях.** Watcher + события editor/tools + очередь изменённых путей; полный rescan только для первичной индексации, восстановления и контролируемой сверки.
2. **Сохранить автоматическое управление без новых обязательных ручных лимитов.** Существующий `RequestBudget` остаётся окончательным gate запроса. `BudgetLedger` — учёт, а не второй произвольный cap. Для локального auto — Stop, контроль прогресса, bounded retries/repair, fan-out/depth; для платного API — явно выбранный денежный/ресурсный бюджет.
3. **Проверять прогресс уже при реализации долгих задач (этап 15).** Развивать `ProgressGuard`/`StageVerifier`: проверяемые результаты, обнаружение повторов, ограниченное восстановление, корректная остановка и сохранение состояния. Не откладывать это до этапа 17.

## 4. Этап 10 — совместимость JSON-агента

**Не реализовывать заново** `json_tools.py`, `neutral.action.v1`, terminal outcomes и защиту от неполного ответа: это уже существует по аудиту.

**Остаток работ:** default prompt/preset для моделей без native tool calling; ограниченное исправление невалидного JSON; понятный compatibility mode; компактные схемы tools; сопоставимые тесты native/JSON. ## 5. Этап 13a — Project Intelligence MVP

**Цель:** точный поиск кода без передачи всего репозитория модели.

### 5.1 Состав MVP

- Индекс файлов и символов для Python, JavaScript, TypeScript; функции, классы, методы, импорты/экспорты, точные source ranges.
- SQLite FTS5 для лексического поиска и `ripgrep`/text fallback при недоступности FTS5 или parser dependency. Parser ошибки не должны блокировать обычное чтение и поиск.
- `search_files`, `search_symbols`, `read_range`, `project_outline`; `find_references` — только с маркировкой точности (LSP/синтаксический/эвристический fallback).
- Состояния UI: **индекс готов / обновляется / требует пересборки / деградированный поиск**; отмена фоновой индексации.
- Индекс — **восстанавливаемый производный кеш**, предпочтительно отдельная cache DB либо короткие пакетные транзакции, без блокировки чатов, checkpoint и UI.

### 5.2 Обязательная схема инкрементальности

1. Первичный scan с учётом `.gitignore`, `.neutralignore`, `WorkspaceAccessPolicy`, исключением бинарных и чувствительных файлов.
2. Объединённый **change feed**: editor save/rename/delete, успешные tool writes/patches, file watcher (debounce/coalescing), terminal-команды с последующей ограниченной сверкой затронутых областей.
3. Durable/восстанавливаемая очередь changed paths, обновление hashes и только затронутых записей; версии файлов и ревизия индекса отдельно.
4. При watcher overflow, потере событий, длительном offline или несоответствии hashes — состояние `needs_rebuild` и контролируемый rescan; не заявлять, что индекс актуален, если подтверждения нет.
5. В MVP 13a/14a использовать только сохранённые файлы. При dirty buffer предлагать сохранить/отменить черновик; текущий dirty guard сохраняется. Overlay переносится за этот MVP: он требует source kind, document id/version, buffer hash и disk base hash в ContextPack → preview → apply; единственный DocumentService проверяет версии и сохраняет editor undo.
6. Неполный `WorkspaceRevisionService.capture` (лимиты обхода) **не является** доказательством неизменности всего проекта. Не подменять им change feed.

**Контракт evidence до интеграции 13a/14a:** разделить результат исполнения проверки
(`exit_code`, outcome, время, command/config hash), её scope/witness (workspace либо
явно определённые файлы/модуль и зависимости) и полноту/актуальность покрытия.
Прошедшая команда не доказывает неизменность всего проекта. Для произвольной
команды без подтверждённого набора зависимостей scope остаётся workspace; incomplete
не повышается до full success. Для ограниченной проверки допустим отдельный
результат «прошла на scoped snapshot» с явной coverage в UI. Изменение dependency
инвалидирует связанное evidence. Новая версия receipts и миграция обязательны;
старые receipts без witness остаются unverified. Контракт реализован отдельной
поставкой: [глава 60](60-scoped-verification-evidence.md). Для workspace сохраняется
строгая сверка полного source tree; явные пользовательские file scopes получают
отдельный scoped success и не подтверждают актуальность всего проекта.

### 5.3 Безопасность и provenance

- Проверять разрешения **на индексировании, retrieval, ContextPack и чтении cached summaries**.
- При отзыве file grant или изменении `.neutralignore` инвалидировать запрещённые записи, summaries и embeddings, если они появятся позднее.
- Каждый источник: canonical workspace id, path, file hash, line range, file/index revision, policy version и статус актуальности.
- Индексатор не получает обходного пути к исполнению команд/чтению файлов вне ToolExecutor/WorkspaceAccessPolicy.

**Gate:** штатные rename/edit/delete/внешнее редактирование обновляются без полного scan; watcher overflow приводит к явному recovery; запрет доступа применяется и к старому кешу; p50/p95 и ресурсы измерены; при отказе индекса доступен прежний поиск и `read_range`.

Ход реализации, измерения и конкретные ограничения 13a — [глава 61](61-project-intelligence-index.md).
Готовность индекса не используется как доказательство полного неизменного дерева.

## 6. Этап 14a — минимальный Intelligent Context Builder

- Сбор кандидатов по задаче из индекса, последних изменений, явных ссылок пользователя и результатов инструментов.
- `ContextPack`: краткая карта, точные фрагменты, сигнатуры, релевантные тесты, причины включения и **source anchors** (path/hash/range/policy version).
- Дедупликация; progressive disclosure: outline → точный диапазон → связанные файлы, без обязательного embeddings и второго inference на каждый поиск.
- **Один финальный gate:** `RequestBudget.fit` и существующая auto-настройка; Context Builder лишь выбирает/ранжирует материал. Не вводить второй token cap или обязательные ручные ползунки.
- Проверять права и актуальность непосредственно перед передачей контекста; при устаревшем hash — обновить фрагмент или сообщить о невозможности подтвердить.
- UI объясняет, какие файлы включены и почему, не показывая запрещённые сведения.

**Gate:** на одинаковых задачах качество правки/тестов не хуже baseline при более экономном контексте; нет запрещённых или заведомо устаревших фрагментов; поведение при недоступном индексе корректно деградирует.

## 7. Этап 11 — Run Registry, Scheduler и Budget Ledger

**Завершён:** [глава 66 — контракты и все gate проверки](66-stage11-complete.md). История: [11a](63-run-registry-scheduler-ledger.md), [11b](64-background-chat-runs.md), [11c](65-process-identity-and-restart.md).

- `RunContext`/`RunRegistry`: независимые идентификаторы и состояния runs, journal, restart/cancel/recovery.
- `RunScheduler`: fair inference lease только на время генерации; при ожидании дочернего run lease освобождается. Для одной локальной GPU — один тяжёлый inference одновременно по умолчанию, с возможностью развития concurrency политики.
- В MVP 11/12 дети наследуют model/connection родителя. Main/Лола/research/probe/repair и служебные генерации используют общий ресурсный арбитраж; lease не освобождается до завершения/закрытия текущего потока. Разные модели требуют отдельного residency/OOM-контракта с provider/resource group. Один inference lease сам по себе не гарантирует единственную модель в VRAM; внешний LM Studio не считается полностью управляемым нами runtime.
- `BudgetLedger` собирает фактические inference HTTP attempts, usage, reservations, tool calls, elapsed time, глубину и fan-out. **Учёт не является самостоятельной политикой остановки.**
- Локальный `auto`: никаких новых произвольных глобальных caps токенов/минут; сохранение Stop, bounded repair/retry, depth/fan-out, watchdog отсутствия прогресса. Для платных API — добровольный явный бюджет.
- Время ожидания пользовательского approval — отдельное состояние, не «зависание» и не ложный loop.
- Общие terminal outcomes/execution contract использовать повторно; не блокировать scheduler до полной переделки JSON-режима.

**Gate:** нет deadlock при parent→child; каскадная отмена; после restart неизвестные эффекты не дублируются; auto-поведение и UX не регрессируют; ledger сходится с реальными вызовами в пределах доступной телеметрии.

## 8. Этап 15 — TaskGraph и долгие задачи с ранним контролем прогресса

**Завершён:** [глава 67 — единый граф, evidence, watchdog, UI и restart](67-taskgraph-and-long-tasks.md).

- Расширить существующие `task_contract.py` и task state с миграцией, **не создавать второй план задач**.
- Подзадачи, зависимости, критерии, affected files, checkpoints и восстановление после смены чата/сжатия контекста/restart.
- Каждый шаг подтверждается evidence: diff, проверка, тест или иной измеримый результат. Текст «готово» без evidence не закрывает шаг.
- Использовать `ProgressGuard`/`StageVerifier` и минимальный `VerificationPlan` **уже здесь**.
- Watchdog различает: повтор одинакового tool call без новой информации, повтор одинаковой ошибки, отсутствие изменения результата после нескольких попыток, ожидание approval, длительную валидную работу инструмента.
- При застое: ограниченная диагностическая попытка → смена стратегии/перепланирование → безопасная остановка с объяснением, журналом и сохранённым checkpoint. Не повторять неизвестные side effects.
- Пользователь видит шаги, может Stop/pause/resume, одобрять опасные действия и корректировать план.

**Gate:** многофайловая задача проходит несколько контекстных циклов, восстанавливается после restart, не зацикливается безгранично, не объявляет успех при провале проверки и не путает approval wait с отсутствием прогресса.

## 9. Этап 12 — субагенты (после Scheduler)

**Завершён:** [реализация и проверки](68-subagent-profiles.md).

**Gate:** отмена/восстановление дерева, корректная передача evidence и отсутствие эскалации прав.

## 10. Этап 16 — Project Memory и гибридный поиск

## 13. Этап 20b — сквозная проверка и release gates

После каждого существенного этапа: unit + integration + Electron smoke (если UI затронут), performance regression, security regression, реальная локальная модель при доступности.

**Обязательные негативные сценарии:** rename/delete, external edit, unsaved buffer, изменение `.neutralignore`, отзыв file grant, interrupted indexing, FTS5/parser отсутствует, binary/large file, symlink/junction, watcher overflow, cache corruption, restart во время tool effect, approval wait, повторяющиеся tool calls.

**Никаких недоказанных заявлений:** индекс, короткий prompt или успешный unit-test сами по себе не доказывают, что модель лучше решает задачи. Отдельно измерять correctness конечного diff и прохождение тестов.

## 14. Правила реализации для Codex

1. **Сначала audit конкретного этапа**: что уже реализовано, какие интерфейсы нельзя дублировать, какие тесты существуют.
2. По актуальному запросу пользователя завершать этап полностью, затем переходить к следующему по зависимостям. Внутри этапа выполнять изменения, проверки и документацию последовательно; не выдавать частичный срез за завершённый этап.
3. Не обходить `ToolExecutor`/`CallJournal`/approval/revision/`WorkspaceAccessPolicy` ради скорости.
4. Не вводить новый обязательный ручной лимит вместо auto; любое новое ограничение обосновывать безопасностью, а не удобством реализации.
5. Cache/index — восстановимые данные, не источник полномочий; canonical SQLite и журналы не блокировать долгой индексацией.
6. Не переписывать рабочие `json_tools.py`, `task_contract.py`, `ProgressGuard`, `StageVerifier`, `RequestBudget` без доказанной необходимости.
7. Для каждого этапа фиксировать: changed files, migrations, тесты, измерения, риски, откат и следующий шаг.
8. Релиз не выпускать с известной регрессией безопасности, повреждением данных или недоказанным заявлением о поддержке модели/оборудования.

## 15. Отдельный трек: Neutral Inference Engine (NIE)

**Статус: исследование, не реализация архитектуры.** Neutral и NIE — два самостоятельных некоммерческих open-source проекта, не привязанных к конкретной сборке ПК. Neutral обязан работать с внешними провайдерами без NIE, NIE — запускаться без Neutral.

**До архитектурного решения:** изучить исходники/документацию llama.cpp/ggml, Strata, KTransformers, vLLM, SGLang, ExLlamaV3, TensorRT-LLM, MLX и Ollama; сравнить dense/MoE, CPU-only, дискретную GPU, unified memory, разные ОС и аппаратные бэкенды. Проверить лицензии исходного кода, зависимостей и моделей. Измерять single-user latency отдельно от серверного throughput.

**Не зафиксировано заранее:** собственный runtime vs обёртка, формат весов, набор бэкендов, лицензия, политика памяти, поддержка моделей. Возможный OpenAI-compatible inference API — кандидат, не утверждённый контракт. Выбор после исследования, прототипов и воспроизводимых benchmark.

**Независимый gate NIE-0:** сравнительный технический отчёт, матрица совместимости и лицензий, 2–3 прототипа ключевых оптимизаций, измерения на разных классах оборудования, затем отдельный архитектурный RFC.

## 16. Ближайший практический спринт

**Sprint 0 (без большой переделки):**

1. Проверить актуальный Git-статус, тесты и интерфейсы этапов 9/55.
2. Зафиксировать baseline 20a: одна локальная модель, три репозитория, задачи и метрики.
