# 67. Этап 15: TaskGraph, evidence и долгие задачи

Статус: **этап 15 завершён по Roadmap V2**, 28 октября 2026,
после [завершения этапа 11](66-stage11-complete.md).

## Один план задачи

Развито существующее `task_contract.py`: canonical `plan_steps` теперь имеет schema 2.
Не создан второй план или конкурирующий executor. Общие lifecycle/stages показывают
фазы работы, а concrete `plan_steps` — пользовательские подзадачи и их зависимости.

Узел содержит `id`, `title`, `kind`, `depends_on`, `affected_files`, `check_ids`,
`status`, ссылки на journal receipts, scoped witness и комментарий. Типы:
исследование, изменение файлов, проверка. Граф ограничен 12 узлами; проверяются
уникальность IDs, неизвестные зависимости, циклы и относительные пути.

Старые строковые шаги мигрируют в `proposed/advisory`, **не** в done. Это сохранённые
предложения, не доказанное выполнение. Активация через `update_task_step` делает такой
шаг обязательным. Новые structured nodes обязательны сразу. Неподтверждённый обязательный
узел не позволяет завершить задачу одной финальной фразой модели.

`set_task_plan` сохраняет user acceptance criteria. Для изменения уже structured
модельного плана требуется `reason`; bounded журнал revisions сохраняет причину.
Закреплённый пользователем план модель не заменяет. Она может обновлять состояния
по evidence, предлагать изменения текстом или остановиться с объяснением.

## Как шаг получает done

`update_task_step` принимает ID, состояние и ссылки `{message_index, call_id}`.
Ссылки берутся из trusted `_receipt` tool result. Произвольное «готово», неизвестный
эффект, отрицательный результат или пользовательское наблюдение без исходной квитанции
не являются автоматическим доказательством исполнения.

| Тип шага | Допустимые доказательства |
| --- | --- |
| Исследование | Успешные чтения/поиск/outline либо bounded child handback; источники и права проверяются заново. |
| Изменение | Успешные mutation receipts и применённые SnapshotStore after states соответствующего chat/journal; affected files должны быть покрыты. |
| Проверка | Настоящий `run_project_command`, связанные пользовательские check IDs и актуальный verification receipt. |

Для пользовательской проверки нужен точный `check_id`, argv/cwd/timeout.
Exit 0 несвязанной команды не присваивается выбранному пользователем критерию и
не позволяет подменить evidence scope. Это правило сохранено, описание инструмента
и ошибка шага теперь явно объясняют его модели.

При завершении фиксируется scoped witness только затронутых путей. Учитываются
файлы, отсутствие после delete и существование каталогов. Внешний edit, rollback,
изменение policy или провал/устаревание check, затрагивающие его evidence, делают узел stale; done-зависимости
тоже становятся stale. Полный fingerprint всего большого проекта не требуется.
Команда со scoped receipt не выдаётся за подтверждение актуальности всего проекта.

Evidence доказывает действие и состояние источника. Семантическое соответствие
произвольному требованию не угадывается по названию узла: для этого нужны подходящие
проверки и пользовательские критерии.

## Контекст, checkpoint и restart

IDs/статусы/dependencies текущего графа входят в компактное состояние задачи.
Canonical история и journal остаются на диске. Сжатие больших tool outputs и архивы
завершённых обменов теперь сохраняют `_receipt` и SHA исходного файла отдельно от
`result_sha256` сокращаемого результата: result-message index не путается с
assistant-batch index журнала. Для чтения полного результата используется прежний
`read_tool_result`; действие не нужно повторять ради вывода.

Checkpoint содержит узлы, evidence, witness, revisions и watchdog hashes. После
переключения чата, сжатия и restart состояния восстанавливаются и проверяются через
существующие SessionService/CallJournal/StageVerifier. Старые approvals не оживают.
Неизвестные effects требуют прежнего explicit recovery, а не повторного исполнения.

`read_file` теперь возвращает стабильный SHA-256, читает bounded bytes с проверкой
статистики и сохраняет CRLF. Это дополнение протокола, лимит file tool не расширен.
В общей проверке найден краткий Windows sharing violation при editor save и index
read: только отказавший atomic replace повторяется кратко, с повторной проверкой SHA
и целевого пути. Изменившийся источник по-прежнему требует нового diff/approval.

## Контроль отсутствия прогресса

Развит существующий `ProgressGuard`. Он сравнивает результат и повтор одинаковой
ошибки, включая меняющиеся аргументы. Receipt IDs, timestamps, run IDs и прочая
служебная metadata не маскируют повтор. Изменившиеся данные чтения считаются новой
информацией, даже если имя и аргументы вызова прежние.

При повторе разрешена одна диагностическая попытка: только чтение и metadata плана,
без записи, команд или нового ребёнка. При следующем повторе — пауза с причиной и
checkpoint. Счётчик диагностики переживает resume; модель не обнуляет его своим
перепланированием. Явная пользовательская правка плана разрешает новую стратегию.

Watchdog наблюдает завершившиеся результаты, а не длительность валидного инструмента.
Approval wait не считается зависанием. Local auto не получил суммарный таймер или
token cap. Прежние Stop, timeout конкретного HTTP и bounded JSON repair/retry сохранены.

## Управление из интерфейса

В «Работе модели» появился concrete план со статусами, зависимостями, affected files
и числом квитанций. После Stop/паузы доступны «Добавить план»/«Изменить план»:
можно менять шаги, выбирать зависимости и заданные проверки, добавлять и удалять узлы.
Циклы и неизвестные проверки отвергаются сервером. Escape закрывает редактор.
В режиме только чтения допустимы только шаги исследования.

Сохранение не запускает модель или программы. Завершённый task checkpoint становится
paused, если появился неподтверждённый шаг; завершённый run epoch остаётся завершённым.
После правки checks-only задача продолжает работу как задача агента, с выбранной
моделью и прежними разрешениями, только по явному Resume. Обычно write/command/source
approvals по-прежнему обязательны. Переключение чата не смешивает его план с чужим.
