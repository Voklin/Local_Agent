# Этап 16: память проекта и поиск по решениям

1 ноября 2026. Возвращение к [основному roadmap](57-roadmap-v2.md) после этапов 11/15/12, качества ответов и интеграции Studio.

## Что получает пользователь

IDE → слева **Память** открывает решения и наблюдения. Можно добавить решение, факт о файле или гипотезу; указать до четырёх относительных путей; увидеть время, происхождение и SHA-256; исправить формулировку и удалить запись с подтверждением. Поиск учитывает текст и пути. «Обновить сведения» заново сверяет источники. Чтение/CRUD не вызывают LLM. Черновик не теряется при CAS конфликте или смене проекта.

В Настройки → Расширения → Плагины есть **Память проекта**. Выключение убирает memory tools и автоматическую проекцию у следующих IDE задач. Личный Chat и Лола не получают память проекта автоматически. Исходные чаты и семь полей справочных заметок сохранены.

## Разделение данных

| Данные | Хранение и смысл |
|---|---|
| Канонический диалог | Существующая SQLite история; поиск памяти её не заменяет и не переписывает |
| Выполнение и проверки | Существующие checkpoint/CallJournal/evidence; наблюдение памяти содержит ссылку на chat/journal/call |
| Решение пользователя | Record decision; source_current значит совпадение источника, не истинность решения |
| Факт о файле | Пользовательская формулировка с SHA источника либо детерминированное наблюдение успешного file receipt |
| Гипотеза | Любое model-authored remember_project_note, даже если модель просит назвать это фактом |
| Проверка | Только историческая scoped command receipt с exit code и объявленной областью; не текущая проверка всего проекта |
| Состояние задачи | Историческая ссылка на завершённый checkpoint, не новая инструкция |
| Legacy/model summaries | Сохранены в редакторе; без provenance не подаются автоматически как актуальные сведения |

Новый каталог knowledge.json находится рядом с существующим memory.json, вне проекта, с тем же per-project ключом и MEMORY_LOCK. SQLite schema 3 не меняется. Запись — atomic replace, revision включает оба каталога; повреждение сообщается, исходник не исправляется и не удаляется молча. Идентификаторы, timestamps, origin, policy и хеши создаёт host. При ручном исправлении сохранено краткое supersedes происхождение. Чтение не обновляет дату создания.

## Поиск и инвалидация

[ProjectKnowledge](../agent/project_knowledge.py) объединяет лексическое совпадение текста и структурное совпадение пути. Релевантные решения приоритетнее повторных наблюдений чтения. Embeddings и вторая модель не обязательны. При новом чате IDE выбираются релевантные записи; нет передачи всей истории или полного дерева файлов.

Для каждого источника сверяются WorkspaceAccessPolicy, neutralignore, ancestor gitignore, root boundary и полный SHA-256. Изменённый файл → stale, удалённый → missing, отзыв доступа → revoked, смена policy → stale_policy. Такие записи целиком исключаются из model projection, но видны пользователю в редакторе. Даже решение без файлов привязано к версии политики. Политика перечитывается после хеширования.

Ограничения памяти — 120 записей, bounded каталог, 600 символов записи, до четырёх источников, до 12 записей и 3200 символов проекции плюс до 1200 символов свежих user notes. Хешируется не больше выбранного набора, с ограниченным IO/time; большой/неуспевающий источник становится unverified, а не блокирует работу с проектом. Никаких новых совокупных лимитов токенов или времени задач. Окончательный gate запроса остаётся RequestBudget.fit/check.

Проекция — отдельное справочное сообщение с host metadata; перед API metadata удаляется. Перед POST, после inference queue и при retry ModelClient проверяет её ещё раз и удаляет изменённую проекцию. Сохранённый результат memory tool тоже перечитывается по provenance; изменённый текст не подменяется новыми несогласованными данными. Полная artifact-запись не обходит отзыв доступа. Canonical history остаётся неизменной.

## Модель и внешние API

IDE получает search_project_memory и remember_project_note через обычный ExtensionService/ToolPolicy/ToolExecutor/CallJournal. Readonly режим разрешает поиск, но не сохранение гипотез. Модель привязывает гипотезу только к уже прочитанным успешным receipts того же journal и текущим SHA. Прав или новых путей из текста памяти не возникает.

Автоматическая подача памяти включена только для локального подключения. Поиск памяти для внешней модели требует просмотра/подтверждения конкретного результата через существующий source approval. При отказе данные не возвращаются модели. Фоновые наблюдения извлекаются из receipts без копирования raw кода и без нового LLM запроса. Существующее optional обновление старого summary сохранено, но не перезаписывает user-owned заметки и проверяет revision перед записью.

## Проверки

Финальный regression: **475 unit tests (2 platform skips), 123 Core/HTTP tests**, npm build, полный Electron Studio smoke и генерация/проверка документации прошли. Полный UI сценарий сделал 23 synthetic HTTP; memory CRUD/source checks не сделали ни одного model call. В отдельном safety-наборе 14 проверок прошли. Ожидаемые TTS timeout/disconnect сообщения в HTTP-журнале относятся к отрицательным fixtures, итог OK.

Журналы: .test-data/stage16-unit-final.log, stage16-http-final.log, stage16-build-verified.log, stage16-electron-final.log, stage16-final-safety.log. Снимок полного UI результата сохранён отдельно в stage16-electron-full-result.json. После этих проверок сделана только CSS правка одноколоночного окна; она прошла отдельный целевой UI smoke на новой сборке (stage16-build-ui-final.log, stage16-electron-memory-final.log).

Проверены новый чат с релевантным решением, сохранение гипотезы модели, внешняя правка/удаление/отзыв доступа, CAS, изоляция roots, ограниченный prompt и настоящий HTTP 500 → retry с исключением изменившихся данных. Настоящий Electron проверил CRUD, stale UI и отсутствие model calls на редактирование. Снимки stage16-memory-records.png и stage16-memory-stale.png находятся в .test-data/studio-smoke; окно осмотрено визуально.

LM Studio доступен, но на момент проверки список загруженных моделей пуст (.test-data/stage16-lm-status.log). Поэтому качество реального LLM-recall не объявлено проверенным. HTTP fixture доказывает контракты и права, а не интеллектуальную полезность памяти на произвольном проекте.
