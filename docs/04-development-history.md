# 4. Этапы развития и использованные решения

## Как читать историю честно

Имена архивов, подписи коммитов и строки внутри файлов не всегда совпадают. В репозитории есть коммит `41187ec` с сообщением `version v5.7`, но его дерево уже содержит `VERSION` со значением `5.8.0`, `model_manager.py` и описание v5.8. Поэтому номер из commit message нельзя считать исчерпывающим описанием содержимого.

Для текущего состояния опирайтесь на код и проверенные коммиты ниже. Более ранние версии описаны по сохранённому README и Git-метаданным. Здесь не утверждается точная дата появления каждой старой функции без соответствующего diff.

## Этап A. Python-приложение и локальные файловые инструменты

Сохранённая ранняя документация описывает приложение для Windows на Python/PySide6 с подключением OpenAI-совместимого сервера. На этом уровне сформировались `security.py`, `tools.py`, история чатов и подтверждение записи. Инструменты — обычные Python-функции, а модель получает JSON-описания их параметров.

Ключевая идея этапа: файловую операцию выполняет приложение, а модель лишь предлагает её имя и аргументы. Разрешение пути и согласие пользователя нельзя поручать текстовому ответу модели.

## Этап B. Долговременное состояние и контекст

Исторический README v5.6.8 описывает контрольные точки и этапы задачи. Появляются раздельные данные: история диалога, компактная память проекта и контрольная точка выполнения. `conversation.py` ограничивает историю, отправляемую модели, без намеренного изменения исходного списка сообщений на входе.

Записи хранятся в JSON вне рабочей папки. Для отделения проектов и чатов используются ID и SHA-256-ключи. Это способ адресации записей, а не шифрование их содержимого.

## Этап C. Примитивы архитектуры v5.7/v5.8

В истории за 19 октября 2026 года есть версии v5.6.x, `ced978a` и `41187ec`. В коде этой линии видны `TaskPlanner`, `StageVerifier`, `ContextManager`, `SkillManager`, `MCPRegistry`, затем `ModelGateway` и `LocalRuntime`.

Здесь сформированы границы для планирования, навыков и разных источников моделей. Однако реестр MCP не запускает серверы и не выполняет MCP tools. `StageVerifier` не вызывается автоматически внутри текущего основного цикла. Подробный статус описан в [главе 11](11-current-status.md).

## Этап D. Применение дизайна Agent Studio

В переданной рабочей папке сохранены `design_reference/agent_studio_reference.py` и пояснение к нему. Большой прототип показывает желаемые визуальные элементы: тёмную IDE-палитру, боковые панели, вкладки, чат и диалоги.

Текущий `agent/ui.py` — отдельная реализация Qt GUI, использующая свои виджеты и существующее ядро. Эталон не импортируется в `main.py` и не становится альтернативной системой разрешений. Нельзя переносить в описание рабочего приложения функции `Runner.tool`, `run_cmd` или `fs_delete` только потому, что они есть в эталоне.

## Этап E. Переданный preview Electron + React + Python

В исходной папке v6 уже присутствовали `apps/desktop`, Python JSON-lines bridge и документы миграции. Оболочка умела выбирать папку, перечислять файлы и читать текст, а отправка задачи показывала демонстрационный ответ.

Использованы TypeScript, React, Electron, Vite, npm workspaces и stdio-мост к Python. Это подготовило границы процессов, но ещё не связывало интерфейс с циклом модели.

## Этап F. Подключение действующего ядра, 22 октября 2026

Проверенный опубликованный коммит: [`9a280b3`](https://github.com/Voklin/Local_Agent/commit/9a280b35afa99306ca593009357488e07973eb61).

Из `AgentWorker` выделен `AgentEngine`. Qt-класс стал адаптером, а `TaskService` получил отдельный поток исполнения, модельные настройки, работу с чатами, checkpoint и коррелированное подтверждение записи. Electron получил узкий набор IPC-обработчиков, проверку отправителя и передачу событий.

Также исправлена несовместимость `@vitejs/plugin-react: latest` с используемой веткой Vite, добавлен lock-файл и обновлён Electron до версии 45. Создан Windows workflow. Для этой версии прошли 36 основных тестов и 15 migration-тестов, сборка и скрытый сквозной Electron-тест с HTTP-фикстурой.

## Этап G. Потоковый текст, отмена и настройки

Проверенный опубликованный коммит: [`1482424`](https://github.com/Voklin/Local_Agent/commit/1482424ac2db61d47289773a4bd1ba0b911151fe).

Добавлен `ModelClient`: asyncio-сеть в отдельном потоке с синхронным интерфейсом для существующего движка. Это позволяет отменить запрос до заголовков, посреди SSE или во время обновления памяти. `ModelStream` использует ограниченную очередь; `TaskService` собирает мелкие фрагменты, а React обновляет одно сообщение по `message_id`.

`model_preferences.py` сохраняет только URL и модель. API-ключ не сериализуется этим модулем. При отмене сохраняется показанный текст без незаконченных фрагментов tool call.

Проверки расширены до 39 основных и 21 migration-теста. Скрытый тест Electron проверяет запись после diff, поток без дубля, восстановление настроек и остановку зависшего соединения. Эти 60 Python-тестов и сборка прошли также в Windows GitHub Actions. Пользователь отдельно подтвердил работу своей модели на предшествующей версии подключения.

## Этап H. Учебная документация

Текущее изменение добавляет объяснение архитектуры, историю, справочники объявлений и воспроизводимую генерацию каталога. Оно не добавляет возможностей модели или файловых инструментов. Ссылки на коммиты выше позволяют сопоставлять объяснения с проверенным состоянием кода.

Локальные коммиты `f3c853a`/`cb50ad3` и опубликованные `9a280b3`/`1482424` имеют соответствующие одинаковые деревья файлов, но разные метаданные создания. В линейную историю опубликованной ветки входят опубликованные SHA; локальные резервные ветки не обозначают дополнительные функциональные этапы.

## Этап I. Полная история и единый контекст

После плана автономной работы исправлена потеря старых сообщений при сокращении модельного контекста. Канонический transcript остаётся полным, а единый builder создаёт независимую проекцию для HTTP с целыми tool-парами и точным ограничением длины сериализованного JSON messages. Обязательные инструкции, текущий запрос и аргументы инструментов не обрезаются молча. Неполные пары от отменённого запуска остаются в архиве, но не уходят в следующий запрос модели.

Снимки истории публикуются после ответов и результатов tools, при завершении и ошибках. Исправлено дублирование prompt в Qt. Дополнительная реальная проверка с локальным LM Studio и уже загруженной qwen3.5-4b: 40 старых сообщений сохранены, тестовый файл прочитан инструментом, точный маркер возвращён пользователю. Потребовалось заменить именованный объект принудительного tool_choice на единственное определение tool с required; сервер подтвердил совместимость этого варианта. Сценарии используют только временные тестовые папки.

Регрессии покрывают полный архив после HTTP tool loop/reopen, независимость вложенных словарей, неполные tool-пары, JSON-экранирование, превышение обязательного бюджета и принудительный первый инструмент. Дальнейшая работа и результаты публикации отмечаются в [рабочем плане](WORK_PLAN.md).
