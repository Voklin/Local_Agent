# 10. Проверки и диагностика

## Что подтверждено

Для базовой версии `1482424` прошли 39 основных тестов и 21 migration-тест, TypeScript-проверки renderer/main/preload и production build. Эти команды также успешно выполнились в Windows GitHub Actions. Скрытый реальный Electron smoke-тест был запущен отдельно локально.

Число Python-тестов относится к внешним unittest cases: `run_sandbox_self_test` внутри одного теста дополнительно выполняет собственный набор. Результат symlink-подпроверки зависит от возможностей ОС. Не нужно складывать внутренние и внешние числа, чтобы получить искусственно больший показатель покрытия.

В этапе approval snapshot локально прошли 51 основной и 24 migration-теста (75 всего), production build, справочники и расширенный Electron smoke с конфликтом diff. Реальный LM Studio подтвердил чтение, обычную запись после approval и отказ при внешнем изменении. Результаты CI конкретного опубликованного commit отмечаются в рабочем плане.

## Команды

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m unittest discover -s tests/migration -v
npm run typecheck
npm run build
```

Запускайте две discovery-команды отдельно: папка `tests/migration` не включена автоматически в первый набор в текущей структуре. Для воспроизводимого запуска тестов адаптера Qt установите полный `requirements.txt`. Для самого приложения Electron достаточно `requirements-core.txt`.

## Почему нужны HTTP-фикстуры

Настоящая LLM может выбрать другой инструмент или сформулировать ответ иначе. Для проверки нашего кода используются HTTP-серверы с фиксированными ответами. `ModelHandler` выдаёт write proposal и финал; `SlowHandler` намеренно задерживает заголовки или данные, чтобы проверить остановку.

Важное различие: проверка «поток задачи завершился быстро» недостаточна для сетевой отмены. Тесты дополнительно ожидают закрытие фактического TCP-соединения на стороне сервера. Они не проверяют, прекращает ли конкретный inference-сервер вычисления на GPU.

## Скрытый Electron smoke-тест

Сначала соберите приложение и запустите Vite на 5173:

```powershell
npm run build
npm exec --workspace apps/desktop vite -- --host 127.0.0.1 --port 5173
```

В другом терминале задайте Python и запустите тест:

```powershell
$env:LCA_PYTHON = (Resolve-Path .venv/Scripts/python.exe).Path
.\node_modules\electron\dist\electron.exe tests/electron/smoke.cjs
```

Тест создаёт временный проект в `.test-data/electron-smoke`, скрывает своё окно, подменяет ответ системного выбора папки, поднимает HTTP-фикстуру и взаимодействует с настоящими DOM-элементами. Он также меняет файл между diff и Apply и проверяет отказ с видимым сообщением. Проверяет отсутствие файла до согласия, текст diff, появление файла после нажатия, частичный ответ без дубля, восстановление настроек после reload и кнопку остановки.

Результат пишется в `result.json`; снимки `approval.png` и `completed.png` помогают визуальной проверке. На Windows запуск GUI-exe из оболочки может вернуть управление без ожидаемого вывода. Для надёжного ожидания используйте `Start-Process -WindowStyle Hidden -Wait`; проверяйте JSON-результат, а не только отсутствие текста в консоли.

## Что делает CI

Workflow [validate.yml](../.github/workflows/validate.yml) использует Windows, Python 3.12 и Node 24. Он устанавливает Python-зависимости, выполняет обе группы тестов, делает `npm ci` с отключённой загрузкой Electron binary и собирает проект. Отдельный hidden UI smoke в workflow пока не запускается: TypeScript/build не являются заменой UI-проверки.

## Разбор неисправностей

| Симптом | Где искать | Первая проверка |
| --- | --- | --- |
| Python Core недоступен | `startBackend`, stderr, `LCA_PYTHON` | Путь ведёт к exe, и в этом Python установлен `openai` |
| `window.lca` отсутствует | Способ запуска | Открыта ли страница в Electron, а не обычном браузере |
| Список моделей пуст | `TaskService.models` | Доступен ли `<base_url>/models`, есть ли загруженная модель |
| Модель найдена, tools не работают | Ответы сервера и `AgentEngine.run` | Поддерживает ли модель/шаблон tool calling |
| Файл открывается в UI, но tool не читает | Лимиты и UTF-8 | UI и tools имеют разные пределы размера |
| Нет записи | `preview_file_change`, событие `change` | Существуют ли родительский каталог и согласие, корректен ли overwrite |
| Задача остановилась сама | `stop_reason`, лог tools | Лимит, повтор одинакового вызова или серия ошибок |
| Ответ повторяется/события чужого чата | `message_id`, `chat_id`, `run_id` | Не потеряна ли фильтрация после рефакторинга |
| После правки Python поведение старое | Дочерний процесс | Полностью перезапустить приложение |
| Ошибка npm dependency tree | `package.json`, lock | Использовать согласованный lock и `npm ci`, не `latest` для случайной замены |
| Тесты пишут в реальные данные | Константы stores | Установить изолированное `LOCALAPPDATA` до импорта или использовать patch |
| Русский CLI-текст вызывает `UnicodeEncodeError` | Кодировка stdout/stderr в Windows | Документационные CLI явно включают UTF-8; проверено и при исходном `PYTHONIOENCODING=cp1252` |

## Безопасная учебная отладка

Работайте с отдельной маленькой папкой, фикстурой или тестом. Печатайте диагностические сведения в stderr, не в stdout моста. Не копируйте целиком служебные чаты в issue без просмотра: они могут содержать текст файлов. Фиксируйте точную команду, интерпретатор, версию кода и ожидаемое поведение — это делает ошибку воспроизводимой.

## Проверки автономного сеанса

Для тестов в ограниченной Windows-среде задавайте TEMP/TMP на `.test-tmp` и LOCALAPPDATA на `.test-data/unit-user` до импорта Python-модулей. Эти каталоги исключены из Git. Сетевым HTTP-фикстурам и LM Studio необходим localhost-доступ; отказ sandbox в сокете не означает ошибку модели. В таком случае повторяется конкретная проверка с соответствующим разрешением среды.

Проверка с реальным LM Studio использовала уже загруженную `qwen3.5-4b`, отдельный временный проект и искусственный маркер в файле. Она подтвердила чтение tool, точный ответ и сохранение 40 старых сообщений; не заменяет детерминированные тесты на отмену/гонки. Текущий сервер отклонил именованный объект tool_choice, поэтому принудительный tool проверяется через единственное определение и required.

### Неблокирующий список моделей

После выноса discovery в отдельный worker локально прошли 51 основной и 30 migration-тестов (81 всего), документационные проверки и реальный скрытый Electron smoke. Новый набор дополнительно проверяет задержанный список моделей параллельно с health/configure, отказ от второго discovery worker, неизменность настроек начатого запроса, отмену сокета и общий deadline для медленно поступающего body. Тот же discovery-клиент получил список от работающего локального LM Studio.

### Восстановление и ошибки хранения

Локально прошли 57 основных и 40 migration-тестов (97 всего), production build и скрытый Electron smoke с видимым предупреждением о повреждённом чате. В CI требуется подтвердить тот же опубликованный commit; результат отмечается в рабочем плане.

Crash-тесты запускают настоящий дочерний Python bridge с временными данными, завершают его до заголовков модели, во время SSE и ожидания approval, затем открывают чат новым процессом. Проверяются paused, сохранённый пользовательский запрос, восстановленный фрагмент ровно один раз и необходимость нового approval. При остановке сервера посреди потока таймер сохраняет черновик без ожидания следующего токена.

Unit/сервисные фикстуры моделируют отказ fsync, недоступный индекс и каталог, повреждённый архив, потерянную отдельную копию checkpoint, ошибку до Apply и разрыв между записью результата tool и checkpoint. Повторённый tool_call_id из старой части истории не считается доказательством успешного нового Apply. Неопределённый исход записи сопровождается предупреждением и проверкой файла пользователем. Это не равнозначно реальному отключению питания или испытанию двух одновременно пишущих экземпляров.

### Windows package

После добавления сквозной проверки Apply/restart текущий набор содержит 57 основных и 41 migration-тест (98 всего). Этот дополнительный subprocess case также входит в 8 тестов frozen Core. Он подтверждает запись, completed checkpoint, сохранение модели и отсутствие ключа в JSON после рестарта.

CI дополнительно содержит windows-package для pull request и main: pinned Python build environment без Qt, frozen Core, 8 subprocess-тестов с урезанным PATH, сборка NSIS и проверка настоящего packaged exe. Успешный job сохраняет только installer как GitHub Actions artifact на 7 дней; это не GitHub Release. Локально frozen Core проверен также через настоящий LM Studio qwen3.5-4b с искусственным файлом и точным маркером. Приёмка установки/обновления/удаления на чистой машине описана отдельно в [главе 14](14-windows-packaging.md).

На Windows CI фиксированное ожидание 1,2 секунды после первого delta оказалось недостаточным: второй фрагмент ещё мог обрабатываться. Crash-тест теперь ожидает весь заданный текст в событиях и соответствующий stream_draft на диске с ограниченным deadline, затем завершает процесс. Тест до заголовков ожидает фактическое подключение до 10 секунд. Фикстурный сервер держит эти crash-соединения до 20 секунд, чтобы сам не завершить сценарий раньше проверяемого kill; боевые сетевые лимиты не меняются.

### План задачи и журнал инструментов

Новый unit-набор task_activity проверяет bounded metadata, разные исходы, отсутствие raw file content, пропущенные этапы и anchored/idempotent recovery. HTTP и subprocess-тесты проверяют сохранённый awaiting_approval, фактические Apply/Reject/FILE_CHANGED и interrupted после kill. Electron smoke дополнен проверками панели и повторного открытия журнала. Текущий набор содержит 62 основных + 42 migration-теста (104 всего); результаты опубликованного изменения и CI фиксируются в рабочем плане.

## Opt-in проверка уже загруженной модели

```powershell
python tools/check_live_model.py --model qwen3.5-4b --output .test-data/live-model.json
```

Этот отдельный CLI не входит в автоматический unittest/CI и не загружает модель специально. Укажите ID уже загруженной модели своего OpenAI-совместимого сервера (при необходимости --url). До импорта Core он создаёт временную AppData и искусственный проект README.md/calculator.py. Последовательно проверяет Chat, IDE (обязательное чтение обоих файлов) и voice persona без озвучки. Любые write approvals отвергаются; после задачи сравниваются хеши искусственных исходников. Успех требует completed, непустой ответ и отсутствие инструментов в Chat/voice. JSON отчёт содержит фактические результаты, code 1 означает неполную/неуспешную проверку. Есть --scenario и ограничение времени --timeout; timeout вызывает cancel. Не подставляйте большой unloaded model: сервер может автоматически начать его загрузку.

Packaged smoke дополнительно открывает голосовую оболочку и перечисляет системные голоса без звука/микрофона. LCA_EXPECT_SYSTEM_VOICE=1 требует хотя бы один установленный голос; без этого необязательная capability может честно показывать error/пустой список на Windows runner. Это не проверка акустического воспроизведения.
