# 22. Мия: разговор и системная озвучка

> Эта глава описывает исходный этап 6.0–6.0.1. Изменения 6.1: [JSON/KV и области чатов](25-json-tools-and-cache.md), [Мия/STT](26-miya-model-and-stt.md), [PC/Telegram](27-desktop-and-telegram.md).
Третий режим теперь позволяет переписываться с Мией и озвучивать её ответы установленным голосом Windows. Это первый рабочий аудиослой, а не полный hands-free ассистент. Микрофон не открывается: STT-провайдер пока не подключён. На проверяемом ПК установлены Irina Desktop (ru-RU), Zira Desktop (en-US), а системных распознавателей нет.

## Действия в интерфейсе

Выберите модель в общих настройках и откройте «Ассистент». Напишите сообщение и отправьте. Кнопка остановки ответа отменяет модельную генерацию, «Stop · голос» отдельно прекращает озвучку. Выберите голос, темп -5–5 и громкость 0–100. «Озвучить ответ» запускает реальный TTS. Автоматическая озвучка новых ответов включается только явным checkbox, по умолчанию выключена. До пользовательского действия звук не воспроизводится. Автоозвучка относится только к новым завершённым ответам; выбранная старая история и остановленные/неполные ответы автоматически не читаются. Одинаковый текст в новом ответе считается новым сообщением, а не дубликатом. Stop также подавляет текущий ожидающий ответ, чтобы озвучка не перезапускалась сразу после остановки.

Озвучивается plain text до 6000 символов, при обрезке показано пояснение. Настройки голоса и auto-play пока живут только в окне и не сохраняются после перезапуска. Переход из голосового режима отменяет собственную озвучку. Каталог можно перечитать; отсутствие голосов/ошибки устройства отображаются, dummy speaking не подменяет результат провайдера.

История общая с личным Chat (project_root пуст), память проекта и file tools выключены. Голосовой режим добавляет в system prompt фиксированный образ Мии — дружелюбного вымышленного персонажа, без утверждений о доступе к микрофону или управлении компьютером. Пользовательские сообщения сохраняются без служебной приставки. В обычном Chat companion flag выключен; в IDE он не заменяет правила файлового доступа.

## Контракты Core

voice_refresh создаёт фоновую операцию catalog, voice_status возвращает state/error/voices/recognizers/sequence/provider, voice_speak принимает text/voice/rate/volume, voice_stop только устанавливает Event. States сервиса: idle/loading/speaking/stopping/error. Повторный запуск запрещён до завершения worker. Каталог имеет deadline 15 секунд, речь — 180 секунд. Bridge продолжает обрабатывать health/Stop, пока процесс работает.

SpeechService запускает только WindowsPowerShell/v1.0/powershell.exe из SystemRoot с -NoProfile/-NonInteractive и постоянным -EncodedCommand. Пользовательский текст передаётся отдельным UTF-8 JSON через stdin; он не вставляется в script, argv или shell expression. Используется SpeechSynthesizer.Speak(String), не SSML. Голос должен быть в полученном каталоге, числа проходят строгую integer/range валидацию. Main пропускает ровно эти четыре поля, дополнительных команд/путей в IPC нет.

Фиксированный script загружает System.Speech (.NET Framework), получает доступные VoiceInfo, выбирает voice/rate/volume и default audio output. Внутреннее действие render используется тестами для WAV и не выставлено renderer/bridge API. Catalog не записывает и не воспроизводит аудио. InstalledRecognizers только перечисляет метаданные, не открывая микрофон.

Worker использует Popen/ProcessJob: собственное дерево завершается при Stop, timeout и падении Core. communicate имеет короткие 100 мс ожидания для cooperative cancellation; output ограничен после получения 100 КБ, сам фиксированный script выдаёт только каталог до 100 записей или маленький JSON result/error. Это trusted system adapter, не механизм исполнения произвольных скриптов модели. Ошибка worker остаётся видимой, окончание работы переводит state в idle/error.

React опрашивает status каждые 500 мс. Начальный discovery отложен и отменяется cleanup, чтобы React StrictMode не запускал и не отменял два каталога подряд. После ухода из режима timer/инициализация/озвучка отменяются. Во время thinking светится орбита, speaking меняет форму рта SVG. Это анимация состояния операции, не lip-sync по фонемам/аудио; prefers-reduced-motion выключает её.

## Проверки и границы

Unit tests проверяют validation до открытия аудио, реальный process single-flight/cancel, JSON с Unicode/кавычками/$HOME, deadline cleanup. Windows integration синтезирует в WAV без динамиков/микрофона; на системе без установленного голоса тест явно skipped. На этом ПК русская фраза дала PCM 22050 Hz, 191027 frames (8,663 секунды). Речь не проигрывалась при автономной проверке.

Service/process tests проверяют voice persona/empty root/no tools и доступность bridge при catalog/cancel. Electron использует настоящий каталог, модельный bridge и всю форму; voice:speak перехватывается тестовым IPC и проверяются payload/speaking/Stop без звука. Ни GUI fixture, ни CI не включают микрофон. Реальная акустическая громкость, качество динамиков и качество распознавания не проверены.

STT, push-to-talk, выбор/установка языковых пакетов, внешние Piper/Whisper провайдеры, wake word, сохранение профиля, Live2D и точная синхронизация рта — отдельный следующий этап. Приложение не устанавливает их автономно. Встроенные Desktop голоса дают локальную озвучку; выбор произвольного стороннего системного голоса подчиняется возможностям/политике его поставщика.

Технологии: [Microsoft SpeechSynthesizer](https://learn.microsoft.com/en-us/dotnet/api/system.speech.synthesis.speechsynthesizer?view=netframework-4.8), [SpeechRecognitionEngine](https://learn.microsoft.com/en-us/dotnet/api/system.speech.recognition.speechrecognitionengine?view=netframework-4.8). Вторая ссылка описывает будущий STT adapter; наличие API не означает, что recognition уже включён.

Дополнительно проверено отсутствие установленных faster_whisper/whisper/vosk/sounddevice в окружении и готовых audio model files в каталоге LM Studio. Модели/языковые пакеты STT не скачивались.
