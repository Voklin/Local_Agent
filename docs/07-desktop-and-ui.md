# 7. Интерфейс, Electron и сборка

## Вход renderer

`index.html` содержит узел для React и ссылку на `src/main.tsx`. Этот модуль вызывает `createRoot` и отображает `App` в `StrictMode`. CSS импортируется здесь. В режиме разработки React может повторно проверять эффекты; поэтому подписка должна возвращать cleanup-функцию.

## Состояние `App`

| Группа | Переменные | Назначение |
| --- | --- | --- |
| Проект | `project`, `root`, `directory`, `files` | Выбранная папка и текущая глубина просмотра |
| Предпросмотр | `selectedFile`, `fileText`, `selectedRef` | Открытый текст и ссылка на актуальный путь из callback |
| Чат | `chat`, `chats`, `chatId`, `runId` | Отображение сообщений, история и фильтрация событий |
| Выполнение | `busy`, `active`, `stopping`, `task` | Блокировка действий, остановка и карточка checkpoint |
| Разрешения | `approval`, `deciding` | Текущее предложение и защита от повторного решения |
| Модель | `baseUrl`, `model`, `apiKey`, `models` | Поля настройки и список ID |
| Инициализация | `settingsReady`, `configuring` | Защита от отправки до загрузки настроек и от повторных операций |
| Навигация | `nav`, `logs`, `health`, `messagesEnd` | Панель, вывод событий, статус и автопрокрутка |

State изменяется через setter-функции React. Ref используется, если callback должен видеть актуальное значение без нового замыкания. Например, callback подписки устанавливается один раз; `runId.current` внутри него актуален, хотя первоначальный state уже изменился.

## Подписка и отображение событий

Первый эффект запрашивает `health` и настройки, затем подключает `onEvent`. Сначала обрабатывается глобальный `backend_stopped`. Остальные события фильтруются по чату и запуску.

Текстовая часть assistant-сообщения хранится как обычная строка. `text_delta` дописывает её, `chat` заменяет финальной версией. `streaming-caret` — визуальный индикатор; он не означает отдельный поток ОС. `task_end` снимает флаги генерации даже при остановке.

React экранирует строки, вставленные как `{m.text}`. Здесь не применяется `dangerouslySetInnerHTML`. Ответы модели не исполняются как JavaScript и не превращаются автоматически в HTML.

## Основные действия

`refreshFiles` запрашивает содержимое каталога; `openFile` либо переходит в каталог, либо читает файл. Переход «..» вычисляется из текущего относительного пути; Python всё равно независимо проверяет границу проекта.

`selectChat` загружает чат и показывает пользовательские/assistant сообщения со строковым `content`. Полные tool results остаются в сохранённом JSON, но не выводятся отдельными сообщениями в истории UI. `refreshChats` обновляет список после завершения задачи.

`discoverModels` сначала передаёт настройки серверу, затем получает ID, выбирает подходящий и сохраняет выбор. `saveSettings` сохраняет введённую конфигурацию без генерации модельного ответа. `sendPrompt` настраивает модель перед стартом; это также передаёт ключ из текущего UI-сеанса в процесс Python.

`decide` передаёт идентификаторы предложения и решение. Диалог — часть React, но факт разрешения проверяет сервис. Закрытие диалога само по себе не доказывает запись; применяется только результат Python-инструмента.

## Preload API

`contextBridge.exposeInMainWorld('lca', {...})` публикует набор функций. Каждая знает фиксированный IPC-канал. Renderer не выбирает произвольный канал и не получает сырой `ipcRenderer`.

`onEvent` создаёт `listener`, подписывает его на `core:event` и возвращает функцию, удаляющую именно этот listener. Так предотвращаются повторные обработчики после переподключения компонента.

TypeScript-описание `Window.lca` находится в `vite-env.d.ts`. Добавление новой операции требует согласовать preload, типы, main IPC и Python dispatch. Полная таблица соответствий — в [главе 8](08-protocols.md).

## Main-процесс

`createWindow` создаёт скрытое окно и показывает его при `ready-to-show`, задаёт размеры и изоляцию. Новые окна запрещаются; внешняя навигация блокируется. Перезагрузка renderer или авария его процесса запрашивает отмену задачи.

`handle` проверяет, что IPC пришёл от основного frame нашего окна. Это фильтр источника команды. Дальнейшая проверка конкретных параметров по-прежнему нужна.

`startBackend` выбирает Python по `LCA_PYTHON` либо системному имени, запускает `bridge.py` с `-u`, устанавливает UTF-8 и читает stdout по строкам. stderr направляется в диагностический вывод, а не разбирается как JSON-команда.

`callBackend` даёт запросу ID и Promise. Таймер ожидания обычного ответа — 10 секунд; pending-запросов допускается не более 100. Длительная задача не занимает Promise на всё время генерации: `start_task` подтверждается быстро, дальнейшие изменения идут событиями.

## Сборочная цепочка

Корневые команды делегируются workspace. `npm run dev` через `concurrently` запускает Vite и отдельную команду, которая собирает Electron main/preload, ждёт TCP-порт 5173 и стартует Electron.

`npm run build` выполняет:

1. `tsc` для renderer.
2. `tsc -p tsconfig.electron.json` для main/preload.
3. `vite build` для HTML, JS и CSS renderer.
4. `build-electron.mjs` для двух CommonJS entry points.

Vite отвечает за преобразование и bundle; отдельный `tsc` нужен для статической проверки типов. Изменение JSX может примениться через HMR, а изменение Python требует перезапуска. Изменение main/preload требует пересборки и перезапуска Electron; текущая dev-команда не является универсальным watcher всех файлов.

## CSS и масштабирование проекта

`style.css` содержит структуру панелей, сообщения, форму модели и modal. Часть исторических селекторов уже не используется новым JSX. Это допустимый технический долг, но удалять их стоит после проверки actual usage.

`App` пока объединяет много обязанностей. Следующий рефакторинг может выделить `ModelSettings`, `ChatPanel`, `ApprovalDialog`, `FileExplorer` и hook подписки. При разделении необходимо сохранить порядок и идентификаторы событий, а не только внешний вид.

## Сообщения о восстановлении

`showWarning` помещает предупреждения storage/recovery в диагностический лог и чат, избегая одинакового сообщения в текущем представлении. Оно обрабатывает warnings в ответах списка/открытия чата и событие warning во время задачи. Повреждённый отдельный чат не скрывает остальные; исходный повреждённый JSON сохраняется для ручного восстановления. При неопределённом результате записи last_event задачи требует проверить файл перед продолжением.

## Упакованное приложение

Production UI загружается из file/ASAR, а Main запускает абсолютный resources/core/lca-core.exe. Он содержит собственный Python и не использует LCA_PYTHON/PATH для поиска интерпретатора. В разработческом пути остаётся исходный bridge.py. Main сохраняет ограниченную lifecycle-диагностику без ключей и содержимого чата. Подробный состав, команды NSIS, pinned environment, packaged smoke и приёмка находятся в [главе 14](14-windows-packaging.md).

## Панель плана и результатов

`TaskProgress.tsx` выделяет из App отображение checkpoint. Типы TaskSnapshot, TaskStage и ToolActivity описывают нужную UI-проекцию. Компонент принимает task, busy и callback resume; он не выполняет tools и не разбирает текст логов. Этапы и структурный журнал обновляются существующим событием task и возвращаются при load_chat. Цвет статуса дополнен текстом; active обозначен aria-current=step. Пропущенные этапы, отклонение, ошибка и неизвестный исход записи различаются. Полный разбор — в [главе 15](15-task-progress.md).
