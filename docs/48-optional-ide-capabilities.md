# Этап 8: дополнительные возможности IDE

Этап начат после завершения проверок этапа 7. Новой обязательной цепочки моделей
нет. Кнопка **«Возможности IDE»** в верхней панели открывает четыре независимых
раздела. Все выключены в новом профиле; изменения нужно сохранить до запуска.
Панель поддерживает оформление Neutral, прокрутку, Esc/крестик и доступный footer.
Закрытие панели не отменяет текущую операцию — для этого есть отдельная кнопка.

## Исследователь

1. Включить исследователя и сохранить предел времени/ответа.
2. Задать вопрос о выбранном проекте и нажать «Исследовать · один запрос».
3. Прочитать отчёт и источники; при необходимости добавить его в поле задачи.
   Передача в основную задачу выполняется только явной кнопкой, без автоотправки.

`readonly_research.collect_sources` ищет до трёх слов вопроса в исходниках, затем
использует имена файлов как fallback. Сканирование ограничено по файлам, байтам
и времени. В запрос попадает до 6 фрагментов первых 120 строк, до 3000 символов
на файл и 12000 суммарно. Распространённые credential-файлы исключены. Это не
универсальный детектор секретов внутри произвольного исходника: выбирайте проект
и API-подключение с учётом отправки этих фрагментов выбранной модели.

Используется основная модель с отдельной историей: один HTTP запрос, без retry,
инструментов, памяти чата, записи, программ и MCP. Chat и Responses используют
существующий request adapter. До HTTP проверяется полный консервативный budget.
Время 10–120 секунд, ответ 256–2048 токенов; defaults 60/1024. Общий `InferenceGate`
занят до реального завершения worker. При Stop HTTP закрывается. Неполный ответ
помечается явно; источники содержат path/line/SHA, показываются elapsed, объём
и reported usage. Отчёт является предложением: его выводы и актуальность нужно
проверять перед изменениями. Качество конкретной локальной модели не выводится
из успешного fixture-запроса.

## Диагностика языка

В разделе «Диагностика» задаются executable установленного LSP, аргументы по одному
на строку, language ID и срок ожидания. Для JavaScript CLI укажите `node` и путь
к скрипту: встроенный Node используется автоматически. Для `.cmd`/`.bat` launchers
нужно указать их фактический interpreter/CLI. Автоматической установки пакетов нет.

Кнопка проверяет выбранный **сохранённый** UTF-8 файл до 256 КБ. Пока в редакторе
есть несохранённые правки, запуск заблокирован. Сервер получает initialize,
initialized и didOpen, затем читается настоящий `publishDiagnostics` для того же
URI/version. До 200 сообщений преобразуются в строки/колонки с единицы. Нажатие
диагностики открывает соответствующую строку. Изменение файла во время проверки
помечает результат stale. Отсутствие publish до срока — ошибка ожидания, а не
«ошибок нет». Push diagnostics — текущий поддержанный сценарий; исключительно
pull-diagnostics серверы требуют будущего расширения.

JSON-RPC использует `Content-Length` в UTF-8 байтах с пределами 8 КБ заголовка/
1 МБ тела. Reader/writer отделены, поэтому зависшая запись didOpen не блокирует
отмену. Server requests, включая applyEdit/executeCommand, отклоняются. Затем
сессия закрывается, дерево процесса уничтожается по deadline. LSP executable
выполняется с правами пользователя и сам может читать проект; это не OS sandbox.
Не используйте неизвестную программу из инструкции репозитория как доверенный LSP.

## Рабочие копии Git

Раздел создаёт detached Git worktree из committed HEAD исходной папки. Ручные
изменения основной копии не копируются, её ветка не переключается. Нужен Git и
выбранный top-level существующего репозитория. На репозиторий допускается 8 копий.
Приложение не делает commit/push/merge или удаление веток.

Копии хранятся отдельно от репозитория в `LocalCodingAgent/wt`; короткий путь и
`core.longpaths` учитывают Windows. Реестр содержит UUID, исходный root, commit,
path и status. `creating` сохраняется до Git, затем `ready`; сбой оставляет
`needs_review` без автоматического повтора. Список сверяется с porcelain `-z`;
open/diff дополнительно проверяют ownership, containment и `git-common-dir`.
Список из открытой управляемой копии ведёт к тому же исходному владельцу.

Кнопки позволяют открыть копию в IDE, показать status/diff и удалить чистую копию
после отдельного подтверждения. Открытая текущая копия, новые commits, изменения,
untracked и ignored-файлы блокируют удаление. Native `git worktree remove`
используется без `--force`; locked/submodule ограничения Git тоже сохраняются.
Нет рекурсивного shell удаления или автоматического prune. Внешние diff/textconv,
hooks/fsmonitor и submodule recursion отключены для служебных команд. Пользовательская
Git-конфигурация, например checkout filters, по-прежнему относится к доверенной среде.
Если Git завершился, а receipt не успел сохраниться, состояние проверяется вручную;
реестр не используется для слепого удаления неизвестного каталога.

## Изолированные команды

Этот переключатель меняет исполнение **обычных команд агента IDE**, включая
пользовательские проверки, на Linux Docker container. Файловые tools и MCP/LSP
остаются отдельными возможностями. Перед каждой командой показываются image,
program, argv, cwd, назначение и ограничения через существующий approval/journal.
В контекст модели добавляется объяснение Linux `/workspace` и readonly проекта.

Фиксированный профиль: `--pull=never`, `--network=none`, readonly root filesystem,
readonly bind только выбранного проекта, user 65534, все capabilities сброшены,
no-new-privileges, 1 CPU, до 64 процессов, RAM 128–2048 МБ, `/tmp` 128 МБ.
Предел команды 1–120 секунд. Используется существующий **локальный** образ; его
загрузка не выполняется автоматически. Аргументы команды стоят после image и
не становятся параметрами Docker. Нельзя добавить host mounts, GPU или privileged.
Команды, которым нужна запись в проект, в этом профиле не поддержаны.

После отмены закрытия Docker CLI недостаточно: runner отдельно удаляет только
свой container с UUID. Неподтверждённый cleanup выдаёт ошибку с именем контейнера
для ручной проверки. Никакого `docker prune`/глобального stop нет.

Кнопка проверки читает наличие Docker и Linux engine. WSL executable обнаруживается
отдельно; это не доказывает наличие дистрибутива и не включает компоненты Windows.
Docker может использовать WSL2 backend. Обычный WSL exec не объявляется sandbox:
он способен обращаться к Windows-дискам. На текущем ПК Docker не найден, поэтому
реальный запуск/отмена Linux container **не проверены**. Проверены argv restrictions,
approval denial и daemon cleanup через fixture. Для полноценной проверки на ПК
потребуются установленный Docker/Linux engine и локальный образ.

## Архитектура, хранение и проверки

`OptionalIdeService` владеет settings/job/cancel, а отдельные adapters не знают React.
Долгий `optional_run` исполняется worker-потоком; bridge продолжает отвечать
health/Stop. Выбор проекта, новые задачи и изменение settings запрещены до конца
job. Settings и root/config снимаются до старта. IPC имеет типы `optionalTypes.ts`,
130-секундный предел и соответствующий cancel. Новых зависимостей нет.

Настройки хранятся в `LocalCodingAgent/optional-ide/settings.json`, receipts — в
`LocalCodingAgent/wt/worktrees.json`. Они не содержат API key и не входят в SQLite
backup истории. Рабочие копии Git тоже не входят в эту копию; сохраняйте нужные
commits/файлы отдельно. Повреждённые settings отключают возможности и показывают
warning вместо падения Core. Плохой worktree registry требует ручной проверки.

14 новых unit-контрактов используют настоящий Git, stdio LSP и localhost HTTP.
HTTP regression проверяет responsive health/cancel, запрет смены проекта во время
зависшего LSP и последующий успешный запуск. Electron проходит пользовательские
opt-in/save/research/diagnostics/create/delete/open и компактный modal footer.
Нагрузочные эффекты измеримы: один запрос исследования, capped sources/output,
elapsed/usage, одна тяжёлая inference и отсутствие фонового исследования при opt-out.
Это не сравнительный benchmark скорости или качества моделей.

Справочники [Python](reference/python.md), [TypeScript](reference/typescript.md),
[тестов](reference/tests.md) содержат все новые объявления с назначением. Итоговые
проверки и installer фиксируются после завершающего прохода ниже.
