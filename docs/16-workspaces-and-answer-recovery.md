# 16. Три режима и восстановление пустого ответа

## Что изменено и почему

В прежнем интерфейсе длинная панель плана занимала верх узкой переписки, а пустой ответ модели мог закончиться статусом completed и общей фразой «посмотри журнал». Это мешало читать результат и скрывало сбой генерации. Теперь подробности открываются кнопкой «Ход задачи», IDE получает более широкую колонку агента, а Chat занимает основное пространство окна. Визуальный ориентир — спокойное пространство разговора Hermes Agent от Nous Research и структура рабочего места VS Code: боковая навигация, проводник, вкладка предпросмотра, вывод и строка состояния. Код Hermes и VS Code в приложение не переносился; это собственный интерфейс LocalAgent.

## Режимы пользователя

| Режим | Сценарий | Доступно сейчас |
| --- | --- | --- |
| Chat | Обычный разговор с выбранной моделью без папки | Отправка, streaming, Stop, сохранение и открытие отдельной истории; файловые tools отключены |
| IDE | Изучение и изменение выбранного проекта | Проводник и readonly preview, агент, инструменты, журнал, diff approval и resume |
| Ассистент | Будущий разговор голосом с аниме-горничной | Отдельный экран, SVG-эскиз и описание будущих компонентов; STT/TTS и анимация ещё не подключены |

Начальное пространство — Chat. Выбор папки переводит в IDE. Во время активного запроса переключение режимов блокируется, чтобы события не попадали в другой контекст. Само переключение сбрасывает выбранный UI-чат, но не удаляет сохранённые разговоры. Их можно открыть в истории соответствующего режима. Черновик composer остаётся в памяти текущего окна; долговременное хранение черновиков не добавлено.

## Область истории и RPC

`list_chats`, `new_chat`, `load_chat`, `start_task` принимают необязательный `mode`: `chat` или `ide`. Для старых клиентов значение по умолчанию — `ide`. Bridge проверяет перечисление; `voice` пока не является модельным RPC-режимом. В Chat область `project_root` равна пустой строке, в IDE — абсолютному выбранному корню. Поэтому история без проекта не смешивается с историей кода. Проверка принадлежности чата в `TaskService` действует и для пустой строки.

React передаёт режим через фиксированные функции preload; main передаёт его в существующие RPC. Произвольный канал IPC не вводится. Параметры preload: `listChats(mode)`, `newChat(mode)`, `loadChat(id, mode)`, `startTask(prompt, resume, mode)`. Смена интерфейсного пространства сама по себе не предоставляет дополнительных инструментов.

`TaskService.start` для пустого корня передаёт `allow_tools=False`, `auto_memory=False`, пустую память. `AgentEngine` меняет system prompt, не подключает проектные навыки и не включает tools/tool_choice в HTTP payload. Если сервер всё же возвращает tool call, engine отклоняет его до preview, approval и исполнения. Нельзя полагаться только на отсутствие схем tools: локальная модель иногда игнорирует протокол.

## Алгоритм восстановления ответа

После каждого SSE-потока engine собирает публичный `content` и tool calls. Пробельная строка также считается пустой. Поток с одними внутренними рассуждениями не является пользовательским ответом; reasoning не показывается и не сохраняется как ответ.

Если нет ни текста, ни tools, движок допускает два дополнительных запроса в рамках общего лимита циклов и времени. К контексту следующего запроса временно добавляется просьба сформировать итог на основе уже полученных результатов. Этот служебный user message не попадает в каноническую историю. В IDE повтор отправляется с `tool_choice=none`: уже исполненные операции не нужно выполнять заново. Если сервер нарушает запрет и присылает tools, вызовы не выполняются, а попытка учитывается как неудачная. В Chat tools отсутствуют во всех запросах.

Успешный итог сохраняется обычным assistant message и завершает задачу. После двух неудачных повторов возникает явная ошибка, задача становится paused, история и результаты инструментов сохраняются. Можно проверить настройки генерации сервера, выбрать другую модель и продолжить. Программа больше не подменяет отсутствие ответа успешным завершением.

В checkpoint поле `answer_retries` хранит последнее записанное количество повторов (при новом повторе счётчик начинается с 1). В лог пишутся finish_reason и булев признак наличия reasoning_content, без самих внутренних рассуждений. Это диагностические сведения, а не доказательство причины сбоя. Пустой ответ может зависеть от модели, chat template, лимита токенов или сервера. Обработка непустого, но обрезанного по length ответа отдельно не изменялась.

Здесь `ref` в React хранит актуальный режим для долгоживущей подписки на события; обычное замыкание эффекта с пустым массивом зависимостей сохранило бы начальный режим. `state` нужен для перерисовки вкладок и компоновки. Область истории (scope) — ключ фильтрации, а не новая папка на диске. Тип TypeScript описывает контракт будущего аудио, но сам по себе не реализует запись или озвучивание.

## Подготовка голоса: следующие шаги

Для работающего голоса нужны выбор STT/TTS-провайдеров, настройки и отдельный слой аудиосессии. Будущая цепочка: нажатие push-to-talk → запись → транскрипция → обычный запрос модели → синтез → воспроизведение. Stop должен прерывать запись, HTTP и воспроизведение. После этого подключаются состояния персонажа listening/thinking/speaking и настройки манеры общения.

Сейчас нет разрешений на микрофон, audio IPC, записи, wake word, TTS, рабочего выбора голоса, Live2D или анимации. `VoiceProfile` и `VoiceSessionState` — только исходные типы, они пока не сериализуются. Эскиз не является окончательным дизайном персонажа.

## Проверки

HTTP-тест воспроизводит write→пустой reasoning-only ответ→успешный текстовый повтор и проверяет единственный tool result, единственную запись и отсутствие служебного user в истории. Другой тест проверяет постоянное молчание: два повтора, failed и paused с сохранением файла. Chat проверяется без папки и без schemas tools, включая отказ от неожиданного tool call. Bridge отдельно проверяет выбор области и отказ неизвестному режиму.

Скрытый Electron smoke проходит через реальные main/preload/bridge/engine: Apply, конфликт устаревшего diff, streaming, восстановление истории, Stop, переключение Chat/IDE/Ассистент и обычный ответ Chat без инструментов. Снимки экрана сохраняются в игнорируемой `.test-data/electron-smoke`. HTTP-фикстура проверяет контракт; она не заменяет проверку с реальной моделью LM Studio.

## Граница завершения worker

CI выявил гонку: сразу после task_end следующий configure_model иногда отклонялся, потому что Python Thread ещё не успел вернуть управление из функции. TaskService теперь хранит task_running: выставляет перед запуском и сбрасывает под RLock после завершения сохранений, непосредственно перед task_end. idle проверяет этот признак под тем же lock. Живой поток, который только возвращается после завершённых событий, больше не блокирует следующий запрос. Детерминированный тест вызывает configure прямо из callback task_end, когда is_alive ещё True; subprocess-тест сохраняет прежнюю проверку немедленного запроса после события.
