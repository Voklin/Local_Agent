# IDE: дирижёр, код, сборка и проверка, 6.7

> Исторический этап 6.7. В Neutral 7.0 эта система удалена по решению пользователя.
> Текущая IDE использует один агентный цикл; прежние настройки ролей и продолжение
> их checkpoint не поддерживаются. История и файлы сохраняются. Актуальное устройство:
> [Neutral 7](36-neutral-guide.md) и [ядро/расширения](37-neutral-core-and-extensions.md).

## Работа в интерфейсе

В IDE рядом с диалогом появился компактный выбор режима: «Одна модель»,
«Дирижёр · полный цикл» и четыре отдельные роли. Кнопка «Роли IDE» открывает
соответствующую вкладку общих настроек; палитра, расположение редактора и оформление
Лолы не заменяются. Текущая роль, модель и состояние отображаются в плане задачи.
Карточка ограничена высотой окна и прокручивается. Режимы Chat и Лола продолжают
работать по прежнему циклу AgentEngine; подключение к проекту требуется только IDE.

1. Откройте папку проекта и настройки «Роли IDE».
2. Выберите провайдер, URL и модель каждой роли. Кнопка «Список моделей» только
   читает каталог. Можно назначить одну основную модель всем ролям.
3. Пустые URL/ID наследуют основную конфигурацию. Ключ роли необязателен; основной
   API-ключ наследуется только для того же URL, другому серверу он не передаётся.
4. Настройте контекст моделей и 0–2 цикла исправлений; сохраните роли.
5. Включите полный цикл либо выберите отдельный этап в IDE и отправьте задачу.
   Каждую предлагаемую запись файла по-прежнему подтверждает пользователь.

По умолчанию роли выключены. Это сохраняет поведение существующих установок и
не загружает четыре модели при открытии настроек. Смена моделей/режима во время
задачи запрещена backend idle guard. Изменение формы остаётся черновиком до Save.

## Обязанности и права

| Роль | Вход и результат | Инструменты |
| --- | --- | --- |
| Дирижёр | Исходный запрос, проект, план архитектуры/файлов и критерии проверки; читает нужные автору существующие файлы. | list_files, read_file, search_text; без записи. |
| Автор кода | План и переданные успешные чтения; полный JSON `files: [{path, content}]`, без изменения диска. | Без файловых инструментов; чистая генерация. |
| Сборщик проекта | Код автора и план; проверяет текущую структуру, предлагает создание/изменение файлов. | Проектные инструменты, включая write_file через исходные diff/revision approvals. |
| Проверяющий | Список реально изменённых файлов, сводка сборщика и статические результаты; JSON verdict pass/revise. | Чтение/поиск, без записи. |

Отдельные режимы запускают только выбранную роль. В частности, «Автор кода»
показывает код, но не создаёт файлы; «Проверяющий» анализирует уже существующий
результат. Полный цикл связывает все четыре этапа. Сложная задача от Лолы,
переданная в IDE, использует выбранную конфигурацию IDE.

Код автора и результаты проверки проходят явную валидацию. Пути автора должны
быть относительными и оставаться внутри проекта с учётом symlink. Ошибка формата
допускает только один повтор с пояснением; это не автоматическое исправление пути
и не разрешение читать/писать вне проекта. Полный код не обрезается: если материалы
не помещаются в бюджет контекста приложения, задача приостанавливается. Контекст
LLM в токенах и бюджет сообщений в символах — разные настройки; оба должны
вмещать задачу и ответ. Результаты других ролей являются данными, а не разрешениями.

## Исполнение и контрольные точки

`IDECoordinator` наследует интерфейс событий AgentEngine и вызывает дочерний
AgentEngine на каждом этапе. Он сохраняет существующий механизм write_approval,
TOCTOU/revision проверки, sandbox и обновления UI. Только сборщик получает
write_file в разрешённых определениях. Автор без tools не может создать файл.
Служебная инструкция роли не меняет полномочия проекта и не предлагается модели
как обычный текст другого участника. Обычный Chat prompt остаётся прежним.

Общий бюджет циклов/инструментов уменьшается после каждого этапа, не сбрасываясь
на каждую модель. Есть общий таймер задачи и пользовательский Stop. Отмена
передаётся текущему HTTP-запросу и ожиданию diff. Старая approval не переносится
между этапами или после перезапуска. Родитель не считает completed одного этапа
завершением всего цикла.

Передачи и результаты хранятся атомарно в
`%LOCALAPPDATA%/LocalCodingAgent/ide-handoffs/<hash-chat-id>.json` вне проекта.
В них входят план, полный код, прочитанный контекст и завершённые роли; это локальные
данные проекта, которые не включаются в Git/установщик. В публичном task checkpoint
показываются только названия/ID/состояния ролей и проверок. Общая история хранит
ответы с подписью роли, не подменяя запрос пользователя служебным prompt.

Resume пропускает завершённые этапы, повторяет незавершённый и требует новых
подтверждений, если сборщик ещё работает. Проверяющий после прерывания повторно
читает файлы. Проверяются проект, исходный prompt и fingerprint настроек; при
смене назначения моделей требуется новая задача либо возврат прежних настроек.
Checkpoint сохраняет исходный prompt до 50 000 символов, как лимит ввода.

После revise автор и сборщик получают замечания; дирижёр не повторяется. Число
исправлений ограничено 0–2. При отклонённой записи, неисправимой ошибке или
исчерпании лимита задача остаётся paused с причиной, а не «успешной».

## Загрузка и выгрузка моделей

`ModelLifecycle` поддерживает:

- LM Studio 0.4+: GET `/api/v1/models`, POST `/api/v1/models/load` и `/unload`.
  Используются точные model key / instance_id. При загрузке задаются выбранный
  context_length, eval_batch_size=128, flash_attention=true и KV-кеш в RAM.
- Ollama: GET `/api/tags`, GET `/api/ps`, POST `/api/generate`. Пустая генерация
  загружает модель, keep_alive=0 выгружает. `num_ctx` задаётся настройкой контекста.
- «Внешний API»: обычные запросы к модели без заявлений об управлении её памятью.

Модели ролей переключаются последовательно. Прежняя выгружается до загрузки
другой, последняя — после завершения/остановки. При одинаковом URL/provider/ID/ключе
соседние роли используют один экземпляр без повторной загрузки. Выгружаются только
назначенные роли, а не произвольные модели пользователя. Посторонняя загруженная
LLM блокирует старт с просьбой освободить память. Параллельные внешние клиенты
сервера не блокируются приложением; гарантируется последовательность запросов
этого цикла, а не глобальная блокировка LM Studio.

Ошибка выгрузки сохраняет active instance и приостанавливает работу; новая модель
поверх него не запускается. Ответы управления проверяются, HTTP читает ограниченный
JSON, не следует redirects и не берёт proxy env. API-ключи — только в памяти Core,
в ide-workflow.json, чат и ответы настроек они не записываются.

HTTP отменяется с проверкой Event каждые 50 мс. Сам сервер может закончить уже
начатую загрузку после разрыва клиента: API отмены серверной загрузки не используется.
При жёстком завершении процесса проверьте список моделей сервера; сохранённый
instance помогает очистке при продолжении. Не обещается контроль GPU offload всех
весов: он остаётся настройкой сервера. Контекст/KV и одна модель сокращают нагрузку,
но не гарантируют, что произвольная большая модель поместится на данной видеокарте.

Официальные протоколы: [LM Studio Load](https://lmstudio.ai/docs/developer/rest/load),
[Unload](https://lmstudio.ai/docs/developer/rest/unload),
[List](https://lmstudio.ai/docs/developer/rest/list),
[Ollama API](https://github.com/ollama/ollama/blob/main/docs/api.md).

## Что считается проверкой

Для реально изменённых .py/.json выполняются безопасные Python AST/JSON проверки
без запуска проектного кода. Для остальных форматов требуется модельный обзор.
Каждый изменённый файл должен быть прочитан текущим проверяющим; чтения учитываются
по реальным успешным tool results, а не тексту «я прочитал». Только pass, пустой
issues, успешные статические проверки и покрытие чтением позволяют completed.
Произвольные shell-команды, npm test, компиляция и браузерные тесты пользовательского
проекта автоматически не запускаются. Модельный обзор не доказывает отсутствие ошибок.

## Публикация

Релизный workflow переведён на ручной workflow_dispatch, чтобы push в draft PR
не публиковал установщик автоматически. Проверки PR продолжают собирать Windows
installer в GitHub Actions artifacts. Веса, WAV, checkpoints и локальный текстовый
корпус Serena исключены из Git. Скрипты обучения остаются доступны отдельно.
Исходники 6.3–6.6, ещё не отправленные ранее, включаются вместе с 6.7, чтобы PR
соответствовал текущему приложению и его оформлению.
