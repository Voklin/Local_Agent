# Этап 5: транзакционное хранилище, миграция и резервные копии

## Что изменилось для пользователя

Чаты Chat/IDE/Лолы, проекты, контрольные точки задач и новые квитанции инструментов
сохраняются в одном локальном профиле SQLite. Первый запуск переносит прежние данные
копированием. Исходные JSON/JSONL остаются на диске; повторного импорта старой истории
при каждом открытии списка больше нет. Режим, проект, закрепление и архив сохраняются.

В **Настройки → История и копии** доступны проверка хранилища, количество разговоров,
сообщений и проектов, итог первого переноса и кнопка сохранения ZIP-копии. Проверки и
резервная копия выполняются после завершения активной задачи. Кнопка открывает обычный
системный диалог сохранения. Отмена не считается успешным экспортом; ошибки видны в
самом разделе. Дизайн использует существующие компоненты и палитру Neutral.

Экспорт отдельного разговора в JSON/Markdown остаётся в меню чата. JSON содержит
полные канонические сообщения, в том числе полный вывод инструментов, без внутренних
ссылок на файлы артефактов. Markdown, как прежде, выводит пользовательские и текстовые
ответы ассистента. Голосовые модели, TTS-корпус и настройки подключений в новую копию
истории не включаются.

## Физический формат профиля

Каталог данных сохранил совместимое имя:
`%LOCALAPPDATA%/LocalCodingAgent/`. Он находится вне выбранного рабочего проекта.

```text
LocalCodingAgent/
  neutral.sqlite3                 каноническая БД
  neutral.sqlite3-wal             возможный активный WAL
  neutral.sqlite3-shm             служебное состояние SQLite
  artifacts/tool-results/ab/
    ab...<64 hex>....utf8          полный результат по SHA-256
  chats/<chat_id>.json             сохранённые исходники старых чатов
  tasks/<hash>.json               сохранённые исходники checkpoint
  tasks/journals/<hash>.jsonl      исходники старых эпох журнала
  projects.json                   исходник прежнего каталога проектов
```

`_atomic_write` в `chat_store` сохранён для настроек и других небольших JSON-файлов.
Новые transcripts и checkpoints через него уже не записываются. `INDEX_FILE`
оставлен для совместимости старого API/диагностики и больше не является индексом БД.

### Таблицы и индексы

| Объект | Назначение |
| --- | --- |
| `chats` | Scope, порядок и две JSON-проекции: metadata с draft/recovery fragments и компактная `summary` для списка. Сообщений и checkpoint в этой JSON-копии нет. |
| `messages` | Канонические сообщения с ключом `(chat_id, position)`; индексы позиций сохраняют anchors этапов 2–4. |
| `tasks` | Один канонический checkpoint по `chat_id`; он добавляется к ответу `load_chat`, а не читается из конкурирующей копии в JSON. |
| `projects` | Название, папка, инструкции, даты и закрепление проекта. |
| `journal_events` | Упорядоченные batch/phase/result/resolution events по chat и journal epoch. |
| `journal_imports` | Однократный импорт эпохи, SHA-256 исходного JSONL, число событий, warning оборванного хвоста. |
| `migration_sources` | Относительный путь, checksum, тип, число объектов/сообщений, статус verified/skipped и ошибка источника. |
| `meta` / `PRAGMA user_version` | Версия схемы, завершённая миграция и доступный поисковый backend. Более новая версия БД отклоняется. |
| `chat_tombstones` | Запрет повторного импорта квитанций удалённого чата. |
| `search_entries` / `history_fts` | Заголовки и user/assistant text; FTS5 trigrams для подстрок, без индекса tool outputs. |

`chat_scope` индексирует mode/project/root/archive и порядок pinned/updated_at.
Список читает компактную `summary`, не загружая все transcripts или большие draft.
Индекс сообщений и внешних результатов при изменении чата обновляется в той же
транзакции. Неизменившиеся сообщения не переписываются через SQL UPDATE.

Поиск нормализует запрос и текст через `casefold`. От трёх символов используется
trigram MATCH с экранированной строкой, область ограничивается выбранным режимом,
проектом, папкой и архивом. Для короткого запроса и SQLite без FTS5 применяется
SQL `instr` по поисковой таблице в нужной области. Этот fallback может сканировать
много поискового текста; полного Python `load_chat` для каждого разговора нет.

## Транзакции и восстановление

`Storage.transaction` открывает `BEGIN IMMEDIATE` до проверки изменяемого состояния.
Вложенные вызовы одного экземпляра используют его connection. При нормальном выходе
выполняется commit, при исключении — rollback; connection закрывается в обоих случаях.
Используются WAL, foreign keys, synchronous FULL и ожидание занятого writer до 15 секунд.

`save_chat(..., checkpoint=True)` атомарно сохраняет metadata, сообщения, индекс и
переданный checkpoint. `TaskService._persist_chat` по умолчанию передаёт
`checkpoint=False`: таймер потокового draft не может затереть более новую задачу,
уже сохранённую движком. Новая задача, task event, recovery и ручная проверка эффекта
сохраняют checkpoint явно. Отдельная JSON-копия задачи больше не нужна.

`JournalTransaction` оборачивает общий thread lock и транзакцию SQLite. Вызовы из
двух процессов не могут одновременно проверить один batch как отсутствующий и
дописать два одинаковых события. Валидация lifecycle и append теперь образуют один
commit. `started` по-прежнему фиксируется до эффекта, а receipt — до UI checkpoint.
Правила `OUTCOME_UNKNOWN`, запрет автоматического повтора и ручное подтверждение
человека из [этапа 2](42-core-execution-and-recovery.md) сохранены.

Удаление чата в одной транзакции убирает messages/search/task/events и сохраняет
tombstone. Исходники миграции и immutable artifact bytes автоматически не удаляются:
это восстановительные материалы, а не видимые чаты. Новая попытка импорта старого
JSON не возвращает удалённый разговор в список. Удаление проекта одной транзакцией
отсоединяет его чаты всех трёх режимов и обновляет обе metadata-проекции.

## Копирующая миграция v1

1. В одной транзакции создаётся схема и проверяется версия.
2. Валидные JSON-чаты копируются с полным порядком сообщений. Заголовок старого
   `index.json` не используется как источник истины.
3. Embedded checkpoint имеет прежний приоритет над отдельным task JSON. Отдельные
   задачи без embedded копии импортируются с проверкой соответствия имени и chat_id.
4. Проекты копируются с прежними IDs и инструкциями.
5. Сверяется число чатов и сообщений; записываются hashes и counts источников.
   Перед общим commit проверяется, что исходники не изменились во время переноса.
6. Только после проверки сохраняется marker завершённой миграции. Сбой раньше этой
   границы откатывает и данные, и версию схемы; следующий запуск может повторить импорт.
7. Старые JSONL эпохи импортируются при первом обращении к эпохе: сначала проверяются
   все events и переходы, затем атомарно копируются и сверяется число записей.

Повреждённый чат сохраняется с warning и не открывается как пустой. Повреждённая
контрольная точка без хорошей embedded копии блокирует продолжение связанного чата:
нельзя считать такую задачу безопасно отсутствующей. Повреждение каталога проектов
останавливает миграцию целиком; после исправления источника её можно повторить.
Оборванный последний JSONL row допускается с warning, полный повреждённый row — нет.
Исходные bytes не ремонтируются на месте.

После успешного переноса старые JSON не являются входом для последующих изменений.
Нельзя запускать старую версию параллельно и ожидать импорта её новых JSON-правок.
Повреждённая каноническая БД даёт явную ошибку; автоматического отката к устаревшей
истории, который мог бы потерять квитанции и повторить эффекты, нет.

## Большие результаты и экспорт

Tool `content` и JSON receipt больше 16 384 UTF-8 bytes сохраняются отдельно. Ссылка
`_neutral_artifact_v1` содержит SHA-256, длину и encoding. Сначала записывается и
синхронизируется полный artifact, затем commit ссылки. Сбой до commit может оставить
неиспользуемый immutable файл, но не частично записанный result в истории.

Путь строится только из проверенного hex digest. Повторное содержимое дедуплицируется;
при чтении сверяются длина и SHA-256. Отсутствие/повреждение result даёт ошибку,
сохраняя историю и исходник для проверки. Повторный tool ради восстановления вывода
не запускается. `load_chat`, восстановление receipts и JSON export гидратируют текст.
`read_tool_result` сохраняет anchors/offset/hash и работу из [этапа 3](43-context-budget-and-economy.md).

Это отделение больших данных **на диске**. Открытый разговор пока загружается в память
целиком; ленивой пагинации renderer и чтения artifact по диапазону с диска ещё нет.
Поиск индексирует пользовательские/assistant тексты, но не stdout/tools и не draft.
Автоматический сборщик неиспользуемых artifacts в этом этапе не вводится.

## Резервная копия и перенос

`Storage.backup` использует SQLite online backup API и получает согласованный snapshot,
а не копирует открытый `neutral.sqlite3` без WAL. Затем архивирует snapshot, только
используемые им artifacts и прежние JSON/JSONL. Не импортированные ранее эпохи JSONL
также сохраняются по рабочему пути `tasks/journals`, чтобы восстановление не потеряло
неизвестные эффекты. В ZIP есть `backup.json` с версией и инструкцией.

До замены целевого ZIP проверяются SQLite quick_check, checksum всех referenced
artifacts, CRC архива и выполняется fsync. При ошибке прежний выбранный ZIP остаётся.
Путь выбирает системный dialog в main, renderer не передаёт произвольный путь. Копия
должна находиться вне активного каталога профиля. В main timeout копирования 300 секунд.

Для восстановления закройте Neutral и сохраните прежний каталог данных отдельно.
Распакуйте архив в **новый пустой профиль**. В его корне должны лежать
`neutral.sqlite3`, `artifacts/` и, при наличии старых эпох, `tasks/journals/`.
`legacy/` содержит сохранённые исходники, не текущие conversations. Не накладывайте
архив на живую БД или остатки чужого WAL/SHM. Настройки подключения и необязательный
голосовой runtime переносятся отдельно. Автоматического восстановления поверх текущих
данных из интерфейса этот этап не добавляет.
