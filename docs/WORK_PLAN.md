# План дальнейшей разработки LocalAgent

Этот документ задаёт последовательность следующих изменений и критерии, по которым можно самостоятельно определить, что этап завершён. Он составлен по состоянию рабочей ветки `codex/electron-agent-bridge` на 22 октября 2026 года. План служит рабочей очередью: после каждого завершённого этапа обновляются статус, документация и описание PR.

## Текущая точка

- Приложение Electron + React запускает Python Core; пользователь подтвердил, что подключение к его модели работает.
- Доступны выбор папки проекта, просмотр файлов, чат, инструменты чтения/поиска, предложение diff, явное применение или отклонение изменений, потоковый ответ, остановка и сохранение рабочих данных.
- Ветка `codex/electron-agent-bridge` опубликована в [PR #1](https://github.com/Voklin/Local_Agent/pull/1). На момент подготовки плана PR открыт как draft; CI для текущей версии прошёл. Слияние не является частью этого плана.
- Рабочая копия была чистой. До правок нужно снова проверить Git, PR, комментарии рецензентов и CI: их состояние может измениться.

## Как продолжать без дополнительных указаний

В начале работы проверьте этот план, `git status`, актуальную ветку и SHA, состояние PR/CI и инструкции `AGENTS.md`. Сопоставьте документацию с текущим кодом. Если появилось замечание рецензента или новый пользовательский ввод, сначала обработайте его. Не перезаписывайте чужие изменения и не сбрасывайте рабочую копию.

Двигайтесь по этапам ниже по порядку и берите следующий только после выполнения критериев текущего этапа. Изменение должно иметь наблюдаемое поведение, ограниченный объём и соответствующие проверки. Исправляйте найденные регрессии до перехода дальше. Обновляйте главы и сгенерированные справочники в том же изменении, когда меняются контракты, алгоритмы, хранение, ограничения или API.

Можно автономно менять код, документацию, локальные тесты, создавать коммиты и обновлять существующую ветку/PR, если GitHub-доступ доступен. Не сливайте PR, не выпускайте установщик и не публикуйте релиз. Не запускайте платные или пользовательские модельные запросы; используйте локальные HTTP-фикстуры. Не отправляйте исходники проекта на внешние сервисы. Если обнаружится необходимость сменить продуктовый сценарий, раскрыть новые полномочия приложения, принять необратимое решение о формате данных или использовать платный сервис, зафиксируйте вопрос и продолжайте независимую безопасную работу.

## Этап 0. Перепроверить исходную точку

**Задача:** продолжить на действительной версии, а не на снимке из документации.

1. Проверить `git status --short --branch`, текущий commit и активный remote; сохранить все существующие незакоммиченные изменения.
2. Прочитать свежие PR-обсуждения, review threads и CI. Проверить, что ветка PR всё ещё соответствует рабочей ветке.
3. Сверить текущие `docs/11-current-status.md` и этот план с реализацией. Если исправление уже внесено, подтвердить его кодом и соответствующей проверкой, затем отметить пункт завершённым.
4. Если CI или review указывает на дефект, сначала исправить его, сохраняя пользовательский сценарий и узкие полномочия Electron bridge.

**Готово, когда:** рабочая база известна, сохранены все локальные изменения, нет необработанной обязательной обратной связи, а пункты следующего этапа всё ещё воспроизводятся в текущем коде.

## Этап 1. Сохранить полную историю чата

**Проблема:** модель получает сокращённый контекст, а движок передаёт обновлённый список сервису, который может заменить им каноническую историю. При длинном диалоге старые сообщения могут исчезнуть из постоянного чата. Вызовы инструментов и ответы инструментов также должны оставаться корректной парой при обрезке контекста.

**Основные области:** `core/python/conversation.py`, `core/python/context_manager.py`, `agent/engine.py`, `core/python/task_service.py`, chat stores и migration tests. Сначала проследить реальные имена по текущему справочнику Python.

**Работа:**

1. Разделить канонический transcript чата и временный список сообщений для одного запроса к модели. Добавление нового пользовательского сообщения и новых событий должно расширять transcript, а сборка контекста для модели не должна переписывать архив.
2. Определить одно место, которое сокращает контекст перед запросом. Сокращение должно сохранять system prompt, последнее сообщение пользователя и целостные блоки tool-call/tool-result.
3. Сохранить обратную совместимость с существующим JSON чатов. Если формат на диске меняется, добавить версию и безопасное чтение старого формата; исходные файлы пользователя не перезаписывать автоматически.
4. Добавить сквозные фикстурные проверки короткого и длинного диалога: полный transcript остаётся на диске; контекст модели ограничен; незавершённые пары инструментов не отправляются; restart/reopen восстанавливает transcript.

**Готово, когда:** после нескольких запусков и сокращения контекста постоянная история сохраняет все сообщения; каждый model request получает валидные сообщения; старые чаты открываются; тесты не требуют реального API.

## Этап 2. Согласовывать запись по неизменённому файлу

**Проблема:** пользователь подтверждает конкретный diff, но файл на диске может измениться между preview и Apply. Тогда утверждённый diff и фактически записанное содержимое могут разойтись.

**Основные области:** `agent/engine.py`, `core/python/task_service.py`, `core/python/bridge.py`, Python tools и UI карточка подтверждения в `apps/desktop`.

**Работа:**

1. При создании предложения сохранить идентификатор предложения, нормализованный путь, ожидаемое исходное состояние файла (хеш или явное отсутствие файла) и новое содержимое.
2. На Apply повторно проверить ID активного запуска и предложения, путь внутри проекта и совпадение текущего состояния файла с подтверждённым снимком.
3. При несовпадении отказать в записи и вернуть понятную ошибку с возможностью заново получить diff. Не применять старый ответ к новому proposal.
4. Убедиться, что повторные, устаревшие и подменённые решения не записывают файл. Проверить обычный Apply, Reject, Cancel, новый файл и конфликт внешнего изменения.

**Готово, когда:** запись возможна только для показанного и ещё актуального предложения, а все отказные пути не меняют файл.

## Этап 3. Укрепить context limits и обработку отказов

После изменения истории проверить ограничения контекста: размер system prompt, большие результаты инструментов, Unicode, файлы с длинными строками и серии вызовов tools. Ограничения должны действовать на окончательно сериализованный запрос и не удалять необходимые tool пары.

Развязать синхронный `list_models` с обработчиком JSON-lines bridge, если текущая реализация по-прежнему блокирует остальные команды до сетевого timeout. Сохранять отклик Stop и UI во время discovery; обрабатывать timeout, неверный JSON и недоступный сервер через обычную форму ошибки. Не добавлять общий сетевой доступ из renderer.

**Готово, когда:** размеры и ошибки ограничены предсказуемо, остальные разрешённые bridge-команды отвечают во время ожидания модели, а фикстурные тесты покрывают timeout и отмену.

## Этап 4. Упорядочить состояние задач и интерфейс восстановления

Проверить crash/restart в точках: до ответа модели, во время потока, во время approval, при Apply и после сохранения результата. Запись чата, индекса и checkpoint должна либо восстанавливаться с ясным статусом, либо сообщать, что согласовать данные автоматически нельзя. Не скрывать ошибки частичной записи.

Уточнить пользовательские состояния: подключение Core, запрос к модели, поток, ожидание решения по файлу, отмена, восстановление и ошибка. Для Qt фиксировать только исправления совместимости; сохранять один источник логики в `AgentEngine`.

**Готово, когда:** после каждого проверенного перезапуска UI показывает корректный чат и статус задачи, а пользователь понимает следующий доступный шаг.

## Этап 5. Подготовить Windows-сборку

Сначала описать и проверить путь установки на чистой Windows-машине без исходного Python-окружения. Затем выбрать воспроизводимый способ включить Python Core и нужные библиотеки в приложение. Проверить запуск, закрытие, каталоги данных, обновление версии и диагностический лог.

Не включать API-ключ в файл настроек, логи или пакет. Хранилище учётных данных проектировать отдельно и добавлять только после проверки поддерживаемого Windows-механизма и восстановления после потери доступа. Текущую разработческую установку не называть готовым установщиком.

**Готово, когда:** сборка устанавливается и запускается на чистой поддерживаемой Windows, не требует установленного Python/Node для пользователя, корректно находит Core и сохраняет пользовательские данные между обновлениями. Для релиза отдельно потребуется явное решение о публикации.

## Этап 6. Принимать дополнительные возможности по одной

После надёжности основных сценариев выбирать следующую возможность по пользовательской пользе и объёму. Возможные отдельные направления: редактор с сохранением, MCP transport, полноценный planner/verifier, локальная GGUF модель, терминал. Наличие старых классов или файлов не означает, что такую функцию нужно автоматически подключать.

Для каждой возможности сначала записать пользовательский сценарий, границы полномочий и критерий готовности. MCP требует явного списка tools и разрешений; терминал требует отдельной модели подтверждений и изоляции; редактор требует согласования внешних изменений файла. Не реализовывать их одним большим этапом.

**Готово, когда:** выбранная функция имеет пользовательский путь в интерфейсе, проверяемый контракт, отказные сценарии и соответствующую документацию; неподключённые заготовки остаются явно обозначены.

## Завершение каждого изменения

Для каждого этапа:

1. Выполнить только проверки, относящиеся к изменению, плюс предусмотренные CI проверки. Если проверка невозможна из-за среды, указать точную причину и не выдавать её за успешную.
2. Обновить handbook и справочники, если поменялись объявления, API, поток данных, хранение или ограничения.
3. Просмотреть diff и `git status`; убедиться, что секреты, пользовательские файлы, окружения и результаты smoke-теста не попали в Git.
4. Создать небольшой коммит с сообщением по содержанию. Обновить существующий PR, проверить опубликованный commit и дождаться CI.
5. Отметить этап ниже, оставить ссылку на commit/PR и кратко записать проверки и оставшиеся риски.

Остановиться на конкретном препятствии, требующем решения владельца проекта, или когда все этапы завершены. Вопросы предпочтений собирать вместе; не прерывать работу ради решения, которое можно безопасно отложить.
