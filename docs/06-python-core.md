# 6. Python-ядро: классы, алгоритмы и данные

Полные сигнатуры и ссылки на строки находятся в [справочнике Python](reference/python.md). Здесь объясняется, как читать реализации и почему они разделены именно так.

## `AgentEngine`: один запуск задачи

Конструктор получает URL, ключ, модель, корень проекта и prompt. Дополнительно принимает историю, память, настройки лимитов, `force_tool`, режим автоматической памяти и ID задачи. Экземпляр содержит флаг остановки, события, состояние approval и checkpoint. После завершения `TaskService` создаёт новый экземпляр для следующего запуска.

`EventHook` — небольшой список callback-функций. `connect` регистрирует callback, `emit` синхронно вызывает их. Это не отдельная очередь сообщений и не Qt event loop. Если callback выполняет медленную операцию, он задерживает вызывающий поток.

`run` состоит из следующих частей:

1. Создание модельного клиента и системного контекста.
2. Подготовка ограничений и счётчиков.
3. Цикл модельных ходов.
4. Сбор текста и tool calls из потока.
5. Разбор JSON аргументов и выполнение инструментов.
6. Проверки остановки, лимитов и повторов.
7. Проверка завершения и необязательное обновление памяти.
8. Сохранение состояния и закрытие сетевого клиента в `finally`.

Защита от зацикливания включает лимит инструментов, подряд идущих ошибок, модельных циклов, времени и шесть одинаковых вызовов подряд. Лимиты не доказывают правильность ответа; они ограничивают объём работы.

| Настройка по умолчанию | Значение | Смысл |
| --- | ---: | --- |
| `max_tool_calls` | 1000 | Суммарные вызовы файловых инструментов |
| `max_consecutive_errors` | 5 | Последовательные ошибки инструментов |
| `max_tokens` | 8192 | Запрашиваемый предел генерации одного вызова |
| `max_entries` | 1000 | Параметр перечисления файлов |
| `max_search_depth` | 15 | Глубина обхода для инструментов |
| `max_agent_turns` | 200 | Число циклов модели |
| `max_context_chars` | 80000 | Целевой размер рабочего контекста в символах |
| `max_runtime_minutes` | 180 | Ограничение длительности; проверяется между циклами |

`max_tokens` не равен `max_context_chars`. Токены считает модель/сервер, а ограничитель контекста проекта использует длину сериализованных строк. В Electron пока нет формы редактирования всех этих лимитов.

## Контроль записи

`_ask_write_approval` создаёт `threading.Event`, публикует запрос и ждёт решения, проверяя остановку. `resolve_write_approval` вызывается со стороны сервиса или Qt-адаптера. В движке сохранены `apply_all` и `reject_all`, но Electron API принимает только отдельные `apply`, `reject`, `cancel`.

`_emit_change` сообщает состояние изменения. Для одного файла может появиться `pending`, затем `applied`, `rejected`, `cancelled` или `error`. История этих событий в UI не является Git-коммитом и не обеспечивает автоматический rollback.

## `ModelClient` и `ModelStream`

`ModelClient.create(stream=True)` возвращает синхронный `ModelStream`. Его async-производитель получает SSE через SDK, а `__next__` читает очередь. При `stream=False` метод ждёт async-future с короткими интервалами проверки флага.

`submit` использует `asyncio.run_coroutine_threadsafe`; возвращается `concurrent.futures.Future`, а не asyncio Task из основного потока. Множество `pending` позволяет отменить все активные запросы. Callback `_forget` удаляет завершённые future.

`close` отменяет задачи loop, ожидает их завершения, закрывает SDK-клиент и останавливает поток. Это обработка ресурсов. Даже если задача не пишет файлов, незакрытые сетевые клиенты и потоки были бы ошибкой сопровождения.

## `TaskService`: состояние процесса

Сервис хранит конфигурацию, выбранный чат, активный движок, поток, `run_id` и текущий `approval_id`. В отличие от экземпляра движка, он переживает несколько задач в рамках одного Python-процесса.

`idle` запрещает переключать чат, настройки или проект, пока поток активен. `start` проверяет данные до запуска, сохраняет пользовательский запрос и подписывает события. `_run` всегда отправляет `task_end` в `finally`.

`_text_delta`, `_flush_text`, `_flush_scheduled` и `_chat_event` согласуют поток и финальное сообщение. Идентификатор сообщения составлен из запуска и номера цикла. `RLock` допускает повторный вход в блокировку в том же потоке; он нужен, потому что обработчики могут вызывать внутренние операции с уже защищённым состоянием.

`select_chat` проверяет формат 32-символьного hex-ID и принадлежность проекта до загрузки. Stores сами по себе не являются полноценным сервисом авторизации: нельзя обходить сервис, напрямую подавая произвольные ID из renderer в файловые функции.

## Файловые инструменты

`TOOL_DEFINITIONS` описывает четыре функции для модели. `execute_tool` — диспетчер, который знает реальные реализации. Если добавить функцию только в JSON-описание, исполнение не появится. Если добавить только Python-функцию, модель не узнает о ней автоматически.

`list_files` поддерживает рекурсивный обход с ограничением глубины и количества записей. `search_text` выполняет поиск подстроки, а не регулярного выражения, возвращает максимум 200 совпадений и обрезает отображаемую строку до 500 символов. UTF-8 чтение имеет ограничение размера.

`preview_file_change` вычисляет unified diff. `write_file` требует `approved=True`, делает preview повторно, пишет временный файл в том же каталоге, выполняет `flush`/`fsync`, снова проверяет путь и вызывает `os.replace`. Параметр `approved` передаётся программным путём; текст модели не может сам установить его через tool arguments.

## Контекст и история

`build_messages` глубоко копирует **всю** каноническую историю и добавляет один новый запрос. Этот список хранится на диске и не сокращается ради модели. Qt передаёт историю до текущего prompt, чтобы не дублировать его. Формат существующего JSON чата не изменён.

Перед каждым HTTP-запросом оба пути движка используют `compact_live_messages`: напрямую или через `ContextManager.build`, который добавляет метаданные task/skills к копии system prompt. `_complete_units` объединяет assistant tool calls со всеми соответствующими tool results. Незавершённые блоки, дубли результатов и осиротевшие tool messages исключаются только из модельной проекции; исходный архив остаётся доступен.

Сохраняются system prompt, исходный запрос текущего запуска, последний user prompt и самый свежий полный блок сообщений. Старые блоки удаляются целиком. Слишком большой вывод инструментов/текст assistant сокращается в копии; вызовы и аргументы инструментов не редактируются. Размер — длина `json.dumps(messages, ensure_ascii=False)`, включая экранирование и метаданные; это не количество токенов и не весь HTTP body. Если обязательные инструкции, запрос или аргументы не помещаются даже после сокращения вывода, вызов модели не выполняется: пользователь получает ошибку с предложением увеличить лимит или сократить запрос.

`select_recent_history` сохранён как самостоятельный совместимый helper с собственными тестами, но построение канонического списка движка его не вызывает. Событие `conversation_updated` передаёт снимок полного списка, а не дельту: получатель заменяет прежний список. Снимки публикуются после ответов, результатов инструментов и при завершении/ошибке/отмене. Произвольное аварийное завершение процесса между этими точками всё ещё может потерять последние данные.

Принудительный первый инструмент отправляется как единственное определение в `tools` с `tool_choice="required"`; далее восстанавливаются весь набор и `auto`. Это проверено с LM Studio, который в текущей конфигурации отклоняет именованный объект `tool_choice`.

## Планирование и проверка результата

`build_plan` создаёт этапы по простому поиску слов действия. Обычный вопрос получает анализ, ответ/проверку и завершение; запрос действия дополнительно получает реализацию. `TaskPlanner.advance` переводит этап дальше. Это детерминированные операции со словарём, а не отдельный интеллектуальный планировщик.

`AgentRuntime.prepare` выбирает навыки и записывает их ID. `working_context` строит контекст. `StageVerifier.verify` существует как отдельная проверка, однако основной движок не вызывает его автоматически. Вместо этого `_verify_task_completion` при необходимости делает отдельный запрос модели и ограничивает число повторных продолжений двумя.

## Skills, MCP и модели GGUF

`SkillManager.discover` читает метаданные `SKILL.md`, `select` оценивает пересечение слов запроса и метаданных, `load` умеет получить полный текст. В текущем `run` в system prompt попадают краткие описания выбранных навыков. Это не запуск отдельных программ.

`MCPRegistry` хранит записи `MCPServer`, флаги и manifest. Транспорта, handshake и исполнения внешних MCP tools в этой реализации нет. `trusted` — поле записи, не самостоятельно работающая граница безопасности.

`ModelManager` сканирует и импортирует GGUF-файлы, `LocalRuntime` запускает `llama-server` и проверяет `/models`. `ModelGateway` представляет выбранный endpoint. Эти классы сохранены и тестируются отдельно, но текущий Electron `TaskService` использует непосредственно введённый URL и `AgentEngine`, а не UI встроенного менеджера GGUF.
